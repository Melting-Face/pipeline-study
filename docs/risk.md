# 리스크 관리 규약 (risk)

이 문서는 **리스크를 어떻게 분류하고, 등급을 어떻게 매기고, 터지기 전과 터진 뒤에
무엇을 하고, 어디에 남기는가**의 규칙 정본이다. 흩어져 있던 도메인별 리스크 서술을
지우지 않고, **분류 축과 등급 산정의 정본만** 여기로 모은다.

> **개별 리스크 항목은 이 문서에 없다.** 항목은 저절로 낡는 상태라
> [`doc-sync.md`](doc-sync.md) §실무 규칙 7의 3축 판정에 따라 저장소 밖으로 나간다.
> 행선지 규칙은 아래 §5.

## 0. 경계

| 문서 | 답하는 질문 |
| --- | --- |
| **이 문서** | 리스크를 어떻게 분류·등급하고 무엇으로 대응하나 |
| [`security.md`](security.md) | 보안·거버넌스 **통제 방침** 자체와 규제 매핑 |
| [`conventions/data-quality.md`](conventions/data-quality.md) | 데이터 품질의 차원과 실패 시 대응 |
| [`conventions/agents/gates.md`](conventions/agents/gates.md) | 실행 **전에 누구의 승인**을 받나 |
| [`doc-sync.md`](doc-sync.md) | 그 문장이 저장소에 남는가 |
| [`operations.md`](operations.md) | 복구 **수단** 자체 — 백업·클러스터 재생성 절차 |

**「대응」은 두 뜻이고 이 문서는 둘 다 담는다.** 나누지 않으면 한쪽이 조용히 빠진다.

| 뜻 | 언제 | 어디 |
| --- | --- | --- |
| **사전** — 이 위험을 어떻게 처리하기로 정하는가 | 터지기 전 | §3 대응 전략 · §4 비가역 |
| **사후** — 실제로 터졌을 때 무엇을 하는가 | 터진 뒤 | §7 인시던트 대응 |

⚠️ **범위 밖**: 복구 *명령*과 백업 *절차*는 [`operations.md`](operations.md)가 갖는다.
§7은 **무엇을 어떤 순서로 판단하는가**만 정하고 명령을 복제하지 않는다.

## 1. 분류 축 4종

| 축 | 무엇이 깨지는가 | 도메인 정본 |
| --- | --- | --- |
| **① 데이터** | 값의 완전성·정합성·거버넌스 | [`conventions/data-quality.md`](conventions/data-quality.md) · [`conventions/analysis.md`](conventions/analysis.md) |
| **② 인프라·운영** | 가용성·자원 예산·복구 가능성 | [`resource-sizing.md`](resource-sizing.md) · [`operations.md`](operations.md) · [`conventions/k8s.md`](conventions/k8s.md) |
| **③ 보안·규제** | 노출·DUA·개인정보·공급망 | [`security.md`](security.md) · [`conventions/publishing.md`](conventions/publishing.md) |
| **④ 이행·기술부채** | 엔진 교체·방언·버전 짝 | [`redesign.md`](redesign.md) · [`architectures/README.md`](architectures/README.md) |

- **축은 배타 분류가 아니라 관측 렌즈다.** 한 사건이 둘에 걸치면 **둘 다 적는다** —
  한쪽으로 몰면 다른 축의 분모에서 그 사건이 사라진다.
- 도메인 정본은 그 축의 리스크를 *서술*하고, 이 문서는 그것을 *등급으로 환산하는 규칙*을 갖는다.
  두 자리가 갈리므로 도메인 문서에서 등급 산정을 다시 정의하지 않는다.

## 2. 등급 산정 — 축이 셋이다

| 축 | 판정 질문 |
| --- | --- |
| **영향** | 깨지면 무엇이 거짓이 되는가 — 값 하나인가, 하위 결론 전부인가 |
| **가능성** | 어떤 조건에서 발동하는가 — 늘인가, 특정 경로에서만인가 |
| **가역성** | 되돌리는 비용이 얼마인가 — §4 |

- 등급은 **★ 5단**으로 적는다. 영향 × 가능성으로 잡은 뒤,
  **비가역이면 한 단 올린다**.
- 🔴 **가역성을 별도 축으로 둔 이유** — 영향과 가능성이 둘 다 낮아도 되돌릴 수 없으면
  실질 등급은 높다. 두 축만으로 재면 그런 작업이 「작은 실수」로 분류되고,
  **그 분류가 게이트를 통과시킨다**. 발행·푸시·볼륨 삭제가 그 자리에 있다.
- **관측되지 않는 리스크의 가능성을 낮게 잡지 않는다.** 안 보이는 것과 안 일어나는 것은
  다른 축이다. 관측 경로가 없으면 가능성은 `미확인`이고 `미확인`은 「낮음」이 아니다 —
  [`conventions/monitoring.md`](conventions/monitoring.md) §3.

## 3. 대응 전략 4종

| 전략 | 뜻 | 이 저장소의 자리 |
| --- | --- | --- |
| **회피** | 그 일을 아예 하지 않는다 | 상시 모니터링 스택 미도입 · Redpanda 미도입 |
| **완화** | 발동 확률이나 영향을 줄인다 | pre-commit 가드 · 읽기 전용 판정 워커 · 버전 상한 |
| **전가** | 다른 주체가 지게 한다 | 오퍼레이터·CNPG에 운영을 맡긴다 |
| **수용** | 알고 진행한다 | 개발 루프 속도 저하 · 단일 호스트 자원 압박 |

- 🔴 **수용에는 근거와 재검토 트리거를 함께 적는다.** 트리거 없는 수용은 방치와 구분되지
  않고, 구분되지 않으면 다음 사람이 그것을 **검토된 결정으로 읽는다**.
  트리거는 **시점이 아니라 조건**으로 적는다 — 조건이 없으면 아무도 그것을 다시 열지 않는다.
- **완화를 골랐으면 §6으로 간다.** 완화는 선언이 아니라 집행을 확인해야 완화다.
- **전가는 책임을 옮기지 실패 확률을 0으로 만들지 않는다.** 맡긴 쪽이 무엇을 보증하는지
  범위를 함께 적는다. 보증 범위를 적을 수 없으면 그것은 전가가 아니라 방치다.

### 어느 전략을 고르는가 — 가역성이 먼저 가른다

전략 넷을 나열하는 것만으로는 고를 수 없다. 순서가 있다.

1. **§4의 비가역 축에 걸리는가.** 걸리면 후보는 **회피와 완화 둘뿐**이다.
   되돌릴 수 없는 것을 「수용」이라 부르면 그것은 검토된 결정이 아니라 도박이고,
   「전가」라 부르면 맡은 쪽도 되돌릴 수 없다는 사실만 가려진다.
2. **발동 조건을 아는가.** 알면 **완화**가 기본값이다 — 조건을 좁히는 게이트를 건다.
   모르면 **회피**하거나, 관측 수단을 먼저 붙이고 **재판정**한다.
   조건을 모른 채 고른 완화는 무엇을 막는지 말할 수 없어 §6에서 닫히지 않는다.
3. **경계를 적을 수 있는가.** 적을 수 있을 때만 **전가**가 성립한다.
4. 위 셋을 통과해 남은 것만 **수용**이며, 이때 근거와 재검토 트리거를 함께 적는다.

## 4. 비가역 작업 — 가역성 축의 정본

이 표가 §2의 셋째 축을 판정하는 근거다. 목록이 여러 문서에 나뉘어 있고 항목이 완전히
같지 않으므로, **가역성 판정만은 여기 한 벌**로 둔다.
승인 절차는 [`conventions/agents/gates.md`](conventions/agents/gates.md),
권한 배선은 [`conventions/agents/permissions.md`](conventions/agents/permissions.md)가 갖는다.

| 작업 | 되돌리는 비용 | 집행 주체 |
| --- | --- | --- |
| git 커밋 | 낮음 — 히스토리 재작성으로 회수 가능 | 사람 승인 |
| git 푸시 | **불가** — 공개 저장소라 푸시가 곧 발행이다 | G2 이후 · 사람 |
| 외부 발신·발행 | **불가** — 캐시·색인이 남는다 | 사람 전담 · 워커 금지 |
| `terraform apply` | 중간 — state와 실자원이 갈릴 수 있다 | 워커는 계획만 → 사람 |
| `kubectl apply` | 중간 — 선언 롤백은 되나 데이터는 아니다 | 워커는 계획만 → 사람 |
| `compose down -v` | **불가** — 볼륨 데이터가 소멸한다 | 워커는 계획만 → 사람 |
| `dbt --full-refresh` | 높음 — 스냅샷 히스토리가 끊긴다 | 워커는 계획만 → 사람 |
| `DROP` · `TRUNCATE` | **불가** | 워커는 계획만 → 사람 |
| `.env` · `tfstate` 수정 | 높음 — 접속 대상·상태가 함께 갈린다 | 사람 승인 |
| 스킬 설치 · lock 편집 | **불가** — 실행 컨텍스트에 외부 코드가 들어온다 | 계획만 → `security` → 사람 |
| 클러스터 재생성 | 높음 — [`operations.md`](operations.md) §4 | 워커는 계획만 → 사람 |

- **「불가」는 기술이 아니라 도달 범위가 정한다.** 로컬에서 지울 수 있어도 이미 나간
  곳에서 못 지우면 비가역이다. 판정 질문은 *"내가 지울 수 있는가"* 가 아니라
  *"내가 못 지우는 사본이 생기는가"* 다.
- **비가역은 사전 게이트다** — 실행한 뒤 검토하는 대상이 아니다.

## 5. 리스크 항목은 어디에 남는가

🔴 **`docs/`에는 규칙만 남고 항목은 나간다.** 판정은
[`doc-sync.md`](doc-sync.md) §실무 규칙 7의 3축을 그대로 쓴다 — 새 규칙이 아니라 적용이다.

| 성격 | 행선지 |
| --- | --- |
| 분류·등급·대응 **규칙**과 그 근거 | `docs/` — 이 문서 |
| 열린 항목 · 공개해도 되는 것 | GitHub Issue — [`conventions/issue.md`](conventions/issue.md) |
| 진행 상태 · 미해결 항목 | 볼트 `status/backlog.md` |
| 보안 실태 · 공격 표면 | 볼트 `security/posture.md` |

- 공개 여부는 **축 3 위협**이 가른다 — 인프라 공격 표면·시크릿 스캔 결함·관측 공백
  지도는 볼트로, 규칙·처방·기능 결함·문서 갭은 Issue로 간다. **갈리면 볼트가 기본값**이다.
- **볼트나 Issue에 먼저 쓰고 `docs/`에서 지운다.** 반대 순서는 손실이 비가역이다.
- 리스크를 문서로 옮기고 싶어지면 그것이 **규칙인지 항목인지** 먼저 묻는다.
  항목을 규칙으로 위장해 넣으면 다음 사람이 낡은 상태를 규칙으로 읽는다.

## 6. 리스크가 닫혔음의 판정

완화 조치를 넣었다는 사실은 그 조치가 **집행된다**는 뜻이 아니다.
[`philosophy.md`](philosophy.md) 원칙 7을 리스크 축에 적용한다.

- **새로 건 게이트는 일부러 위반시켜** 막히는지 본다. 「조치했다」를 「막힌다」로 읽지 않는다.
- **부정 결과는 관측 경로 생존과 함께**만 유효하다. 「0건」은 위반이 없다는 뜻이 아니라,
  먼저 **그 대상이 모집단에 들어갔음**을 증명해야 의미를 갖는다.
- 🔴 **게이트가 초록인 것과 게이트가 옳은 것은 다른 축이다.** 뒤엣것은 위반시켜야 보인다.
  프로브한 축만 「잡는다」고 쓰고, **못 잡는 것도 같은 자리에 적는다**.
- 프로브하지 않은 축은 `미확인`으로 남긴다. `미확인`은 실패가 아니지만 **닫힘도 아니다**.
- 검증 절차의 정본은
  [`conventions/agents/enforcement.md`](conventions/agents/enforcement.md)다 —
  3셀 대조·대조군 우선·차단 문구 출처 구분.

## 7. 위험이 현실화됐을 때 — 사후 대응

§3까지가 터지기 전의 결정이라면 여기는 **터진 뒤의 순서**다.
복구 명령·백업 절차는 [`operations.md`](operations.md)에 있고, 여기서는
**무엇을 어떤 순서로 판단하는가**만 정한다.

> ⚠️ **감지 축은 비어 있다 — 빠뜨린 것이 아니라 선언된 공백이다.**
> 이 저장소는 상시 자동 감지를 **의도적으로 두지 않는다**
> — [`architectures/monitoring.md`](architectures/monitoring.md).
> 그래서 감지 경로는 둘뿐이다: ⓐ **실행이 실패한다** — 빌드·테스트·훅이 빨간불
> ⓑ **사람이 눈으로 발견한다**. 「조용히 잘못된 값」은 **어느 쪽에도 걸리지 않는다**
> — [`conventions/data-quality.md`](conventions/data-quality.md) §2의 사례가 그 자리다.
> ⇒ 대응 시각은 「발생」이 아니라 **「발견」**으로 적는다. 둘을 같은 값으로 적으면
> 감지 지연이 기록에서 사라진다.

**이 공백을 메우는 방향은 하나뿐이다 — 검사를 실행 경로 *안에* 넣는 것.**
현행 게이트 3층은 pre-commit·CI·정의 로드까지이고 **셋 다 파일과 선언만 읽는다**
— [`test.md`](test.md)의 실인프라 계층이 상시 게이트가 아닌 이유와 같은 축이다.
그래서 값을 보는 층은 **실행하는 쪽**에만 생길 수 있고, 그것이
[`conventions/data-quality.md`](conventions/data-quality.md) §5 ⓒ가 선언한 미배선 축이다.

⚠️ **실패 알림은 감지 축을 늘리지 않는다.** 잡 실패를 알리는 sensor는 *이미 실패한 것*을
전달할 뿐 **조용한 실패를 보지 못한다.** 게다가 이 저장소는 외부 발신을 비가역으로 보아
사람 게이트에 두므로, 그 신호가 닿는 곳은 결국 UI이고 **UI를 보는 것은 ⓑ 사람 경로**다.
⇒ 알림을 「감지 추가」로 세면 **사람 경로를 자동화 경로로 오분류**하게 된다.

| 단계 | 무엇을 하는가 | 판정 근거 |
| --- | --- | --- |
| **1 발견** | 발견 시각·발견 경로를 적는다. 발생 시각은 **미확인**으로 둔다 | 위 감지 공백 |
| **2 분류** | 축과 등급을 매긴다. **먼저 「무엇이 이미 나갔는가」에 답한다** | §1 · §2 · §4 |
| **3 초동** | 확산을 멈추고 증거를 보존한 뒤에 고친다 | 아래 순서 규칙 |
| **4 복구** | 복구 조치 자체의 비가역 여부를 다시 판정한다 | §4 · [`operations.md`](operations.md) |
| **5 회고** | 전말·교훈·후속을 셋으로 갈라 각각의 행선지로 보낸다 | §5 |

- **2 분류에서 순서가 뒤집히면 안 된다.** 원인보다 **도달 범위**를 먼저 묻는다 —
  커밋·푸시·발행이 걸려 있으면 §4의 비가역 행이 그대로 적용돼 등급이 올라가고,
  그 등급이 초동의 강도를 정한다. 원인 규명은 그다음이다.
- 🔴 **3 초동의 순서가 규칙이다** — ① 확산을 멈춘다 ② 증거를 보존한다 ③ **그다음** 고친다.
  고치는 것을 먼저 하면 원인 판정 근거가 사라진다. 특히 **재기동·재생성은 증거를 지운다** —
  상태를 스냅샷으로 남기기 전에는 하지 않는다.
- **4 복구에서 「복구 중」은 승인 면제 사유가 아니다.** 복구 조치가 비가역이면
  평시와 같은 게이트를 탄다. 급하다는 사실은 등급을 낮추지 않는다.
- **5 회고의 산출물은 셋이고 행선지가 다르다** — 전말과 수치는 **볼트**, 규칙·처방으로
  일반화되는 교훈은 **`docs/`**, 열린 후속은 **Issue**다. §5의 분기를 그대로 쓴다.
  ⚠️ **「사고가 났다」는 상태이고 「그래서 규칙이 이렇게 바뀐다」는 규칙이다.**
  한 문장에 적으면 규칙이 상태와 함께 낡는다.
- **회고에서 나온 완화는 §6으로 돌아간다** — 일부러 위반시켜 막히는 것을 본 뒤에 닫힌다.
