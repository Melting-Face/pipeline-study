**절 번호(`5-1`~`5-5`)는 분리 후에도 그대로 쓴다.** 다른 문서가 `§5-1`·`§5-3` 형태로
가리키고 있어, 번호를 다시 매기면 경로와 번호가 **동시에** 어긋난다. 바뀐 것은 경로뿐이다.

## 5-1. Spark Connect 어댑터 스모크 — 🗑 철거(Spark Connect·Thrift 철거)

dbt 실행 엔진이 **dbt-trino**(공식 어댑터)로 바뀌어 이 관문이 방어하던 대상
(dbt-spark가 공식 지원하지 않는 Connect 경로, `dbt-spark<1.12`·`pyspark<4.2` 상한)이 함께 사라졌다.
스크립트 `scripts/spark_connect_smoke.py`는 삭제했다(본문은 git 이력).

**절 번호는 비워 둔다** — 다른 문서·이력이 `§5-1`로 가리키고 있어 번호를 당기면 어긋난다.
남는 교훈 둘은 다른 관문이 그대로 쓴다:

- **회귀(`1`)와 판정 불가(`2`)를 나눈다** — 포트가 닫혀 못 붙은 것을 실패로 읽으면 오진,
  통과로 읽으면 관측 경로가 죽은 채 통과다(§5-2 「에러 0건」, §5-4).
- **스모크가 *무엇의* 대리표본인지 적는다** — 통과 신호가 실제보다 넓게 읽히는 것을 막는다.

⚠️ **Trino 이관은 값 대조 없이 했다(미대조).** dbt-trino는 공식 어댑터라 상한·스모크 짝이 필요 없지만,
그것은 *업그레이드 리스크* 축이고 *Spark 시절과 같은 값인가* 축은 열려 있다
([architectures/trino.md](../architectures/trino.md)).

## 5-2. `iceberg_maintenance_job`이 구조적으로 못 하는 것

테스트를 추가하기 전에 **잡 구조가 영영 처리하지 못하는 둘**을 먼저 안다.

**ⓐ 첫 op이 실패하면 뒤가 전부 중단된다.**
의존성이 `optimize → expire snapshots → remove_orphan_files` 순서라,
첫 op이 실패하면 나머지가 `Not executing`으로 건너뛰어진다.
🔴 **순서 강제(안전)와 실패 전파(가용성)가 같은 배선에 묶여 있다** —
"앞 단계가 할 일이 없어서 실패한 것"과 "앞 단계가 깨진 것"은 다른데 구분되지 않는다.

**ⓑ 어떤 테이블에도 속하지 않는 객체를 지울 경로가 없다.**
`remove_orphan_files`는 **인자로 받은 테이블의 location 하위만** 스캔하므로,
카탈로그에서 이미 지워진 테이블의 잔여 객체는 **지목할 대상이 없어 스캔 범위 밖**이다.

📌 **"orphan 정리 잡이 있다"와 "orphan이 정리된다"는 다르다.** 잡의 이름이 커버리지를
실제보다 넓게 들리게 한다 — **테이블 단위 프로시저이지 warehouse 단위 청소기가 아니다.**
고아를 사람이 지웠다면 사라진 것은 **대상**이지 **공백**이 아니다.

⚠️ **0 KiB 디렉터리 마커를 고아로 세지 않는다.** `flink cancel` 뒤 남는 빈 마커는
용량을 먹지 않으므로 같은 목록에 넣지 않는다 — **크기 0이 구분 기준**이다.

### "에러 0건"을 통과로 읽지 않는다

특정 에러가 **0건**인 것을 그 배선의 통과 근거로 읽으면 안 된다.
프로시저가 앞 단계에서 먼저 죽으면 **그 에러가 날 코드 경로가 실행되지 않는다** —
판정은 `통과`가 아니라 **`미검증`** 이다.

§5-1(철거)이 종료코드 `1`과 `2`를 나눈 것과 **같은 구분**인데,
여기서는 **잡이 자동으로 해주지 않으므로 사람이 해야 한다.**

## 5-3. Iceberg changelog 판독 관문 + 소스 적격성 진단 — ⏸ 중단(Spark Connect 철거)

이 관문은 **Iceberg Spark 프로시저 `create_changelog_view`** 를 Spark Connect로 호출했다.
Connect 철거로 실행 경로가 없어져 **중단**한다 — 스크립트 `scripts/iceberg_changelog_probe.py`는
삭제했고(본문·실측 기록은 git 이력), **재수립은 Spark 배치 경로가 서는 미션 C 이후**다.
Trino에는 같은 프로시저가 없다(changelog 뷰는 Spark 전용 기능).

**중단 동안 무엇이 열려 있나**: changelog·증분 조회 경로를 바꿀 때 기댈 관문이 없다.
기존 판정(소스 적격성 — Flink 스트리밍은 append 스냅샷만 본다)은 **실측 당시의 결론**으로 남고
새로 확인된 것이 아니다.

남는 교훈(관문과 무관하게 유효):

- **창은 `committed_at`이 아니라 `parent_id`로 잡는다** — 정렬상 인접한 스냅샷이 부모-자식이라는 보장이 없다.
- **정리 검증은 카탈로그와 스토리지 양쪽을 본다** — `DROP TABLE`은 카탈로그 항목만 지운다.
  스토리지는 **"0개"와 "prefix 자체가 없다"를 함께** 본다.
- **접속 경로는 선언과 실사용이 갈릴 수 있다** — 실행할 때 어느 경로로 붙었는지 함께 적는다.

## 5-4. PhysioNet 접근 판정 — 수동 관문

`uv run scripts/physionet_access_probe.py` — 수집 자산(`raw_*`)을 **처음 켜기 직전** 통과시킨다.
인증 방식·`SHA256SUMS.txt` 형식·슬러그/버전이 전부 **외부 사실**이라 코드가 확인할 수 없다.
⚠️ **핵심은 음성 대조다** — 인증 없이도 받아지는 파일이면 200은 아무것도 증명하지 않는다.
종료코드 `0`=통과 / `1`=Basic 거부(세션 로그인 분기) / `2`=**판정 불가**이며, **`2`를 `0`으로도
`1`로도 읽지 않는다**(§5-1과 같은 규율 — `미확인`). 측정 항목은 스크립트 독스트링.

⚠️ **이 절은 [test.md](../test.md) §계층 표의 "실인프라 예외"에 더하지 않는다** —
붙는 대상이 *우리 실인프라*가 아니라 **외부 서비스**다. "수동 관문"이라는 성질은 같아도
축이 달라 같은 수로 세지 않는다.

## 5-5. S3 호환 스토리지 합격 스위트 — 수동 관문

```shell
uv run scripts/storage_conformance_probe.py --help
uv run scripts/storage_conformance_probe.py --only p1,p2 --keep   # 첫 실행
```

**무엇을 방어하나.** 스토어 교체 후보의 공식 문서가 체크섬 트레일러 축에서 전부 침묵해
**문서로는 후보를 가릴 수 없다**([architectures/storage.md](../architectures/storage.md)).
같은 스크립트를 **대조군(현행)과 후보에 같은 인자로** 겨눠 결과를 나란히 놓는 것이 유일한
판정 수단이다. 이쪽은 **스토어 교체를 판단하기 직전**의 관문이다.

프로브는 5종이다 — P1 SDK 기본 체크섬 PUT · P2 기본 설정 PUT/GET 왕복 ·
P3 pyiceberg write→read + 대용량 멀티파트 · P4 warehouse 나열 대조 ·
P5 path-style·페이지네이션·멀티파트 abort. 각 축의 인자·구현 정본은 스크립트 머리 주석이다.

### 종료 코드 — 앞의 세 관문과 **의미가 다르다**

| 종료 코드 | 의미 |
| --- | --- |
| `0` | 선택한 프로브가 **전부 실행됐다** — 결과에 FAIL이 섞여 있어도 `0`이다 |
| `2` | 하나 이상 **미측정** — 접속 불가·의존성 부재·겨냥한 축이 전선에서 불성립 |
| `3` | **사전 조건 미충족** — 아무것도 못 돌렸다(자격증명·엔드포인트·안전 가드) |
| `1` | **쓰지 않는다** — FAIL을 종료코드로 내면 "못 돈 것"과 뭉쳐진다 |

🔴 **§5-1·§5-3·§5-4의 종료코드 표를 여기 돌려쓰지 않는다.** 저쪽 `0`은 *전부 통과*지만
여기 `0`은 **관측 경로가 살아 있었다**뿐이고 FAIL이 섞인 `0`이 정상 결과다. 표를 재사용하면
`0`이 "전부 통과"로 읽히는데 **그 오독이 정확히 이 스위트가 막으려는 실패 모드**다.
갈래의 기준은 응답 주체다 — 스토어가 응답한 오류는 **FAIL**이고 정보이며,
접속 실패·모듈 부재는 **미측정**이고 정보가 아니다.

### 대조군이 빨간 것을 먼저 보고 나서야 후보의 초록을 믿는다

**현행 스토어는 P1에서 실패해야 정상이다.** 통과하면 스토어가 고쳐진 것이 아니라
**프로브를 의심한다** — 저장소 전역에 깔린 체크섬 우회 설정을 프로브가 명시적으로
덮어쓰지 못하면 SDK 기본 경로를 안 타고 조용히 초록이 난다. 그 초록은 "통과했다"가 아니라
**"그 축을 안 쟀다"** 이고, 둘은 화면에서 같은 모양이다.

### 전제 4종

| 전제 | 왜 |
| --- | --- |
| 대상 스토어가 기동 중 | 미기동은 FAIL이 아니라 **미측정**이다. 종료코드 `2`로 갈린다 |
| **P1은 https 엔드포인트에서만 잰다** | http에서는 트레일러 프레이밍이 생기지 않아 초록이 *안 쟀다*가 된다 |
| 버킷·프리픽스에 `probe` 마커 강제 | allowlist가 실 버킷을 **구조적으로** 배제한다. denylist는 이중 방어 |
| 자격증명은 환경변수로만 | `ICEBERG_S3_*` → 미설정 시 `AWS_*` 폴백. 인자·문서·출력에 값을 싣지 않는다 |

### 첫 실행은 범위를 좁힌다 — `--only p1,p2 --keep`

**첫 실행은 `--only p1,p2 --keep`으로 한다.** 보안 점검에 붙은 조건이다 —
쓰기를 두 프로브로 줄이고, 정리 경로를 신뢰하기 **전에** 무엇이 남았는지 사람이 직접 본다.
확인한 뒤에 `--keep` 없이 전 프로브로 넓힌다.

⚠️ **`--keep`으로 남긴 객체는 확인 직후 지운다.** 남기면 이 관문이 스스로 §5-2 ⓑ의
**"지목할 대상이 없는 고아"** 를 생산한다 — §5-1이 `PURGE`를 쓰는 것과 같은 이유다.

### 이 스위트가 보증하지 않는 것 — 미검사 축 넷

**빠뜨린 것이 아니라 일부러 안 한 것**이라 세어 둔다. 정본은 스크립트 머리 주석 §미검사 축이다.

| 미검사 축 | 왜 남는가 |
| --- | --- |
| Java · AWS SDK v2 경로 | 스위트는 파이썬만 본다. 그런데 **손상은 Java에서도 났다** |
| Hadoop `s3a://` 클라이언트 | P4가 재는 나열은 구현이 다르다. 유지보수 프로시저의 근거로 못 쓴다 |
| barman-cloud WAL 아카이빙 왕복 | 오퍼레이터·플러그인이 필요해 범위 밖이다. P2는 근사이지 등가가 아니다 |
| 성능 · 내구성 · 동시성 | 이 스위트는 **정합성만** 본다 |

⚠️ 첫 행이 급소다 — 교체 동기인 체크섬 결함이 **Java 경로에서도 실재**하는데 판정은
파이썬 축에서만 나온다. **초록 5개를 전 경로 통과로 읽지 않는다.**

### 등재된 것은 실행 규약이지 실행 결과가 아니다

**P1~P5 본체를 실제로 돌린 기록은 없는 상태로 등재됐다.** 이 절이 정하는 것은
*어디에 적혀 있고 어떤 순서로 돌리는가*이고, **관측 경로가 살아 있는지는 첫 실행이 확인한다.**
그전까지 이 관문에 초록은 존재하지 않는다 — 등재를 통과로 읽지 않는다([philosophy.md](../philosophy.md) 원칙 7).
