# 오퍼레이터 패턴 3종 (아키텍처 · 프로젝트 관점)

이 문서는 **「왜 셋 중 둘만 전용 이미지를 굽는가」의 판단축**을 갖는다.
그 축과 3종의 **비교 구조**, 굽는 이유의 **분류**, **재검토 트리거**가 여기 있다.
반대로 **정본이 아닌 것**을 먼저 밝힌다 — CRD 필드·설정 키·함정 상세는
[../conventions/k8s.md](../conventions/k8s.md) §9·§9-2와
[../conventions/k8s/cnpg.md](../conventions/k8s/cnpg.md)가, 자원 수치는
[../resource-sizing.md](../resource-sizing.md)가, 엔진별 결정 배경은
[spark.md](spark.md)·[flink.md](flink.md)·[k8s.md](k8s.md)가 갖는다.
**여기에 복제하지 않는다** — 복제하면 양쪽이 각자 낡는다.

## 개요

오퍼레이터는 **CRD(사용자 정의 리소스) + 조정 루프**다. 사람이 절차를 실행하는 대신
원하는 상태를 오브젝트로 선언하면, 컨트롤러가 실제 상태를 그쪽으로 수렴시킨다.
이 저장소는 컴퓨트·데이터 서비스를 이 패턴으로 셋 돌린다 — **Spark · Flink · PostgreSQL**.

**셋 다 오퍼레이터 자체는 공식 배포판을 그대로 쓴다.** 굽는 것은 오퍼레이터가 아니라
**잡 런타임 이미지**다. 그래서 *"오퍼레이터를 쓰면 이미지를 구워야 하는가"* 라는 물음은
성립하지 않는다 — 오퍼레이터 패턴의 속성이 아니기 때문이다.

## 이 프로젝트에서의 위치 — ✅ 채택

**패턴 자체는 채택 확정**이다. 다만 **개별 엔진의 이행 상태는 각 문서가 갖는다** —
Spark·Flink는 🚧([spark.md](spark.md)·[flink.md](flink.md)), 플랫폼 전체는
[k8s.md](k8s.md)·[terraform.md](terraform.md)다. 이 문서의 ✅를 엔진 이행 완료로 읽지 않는다.

### 1. 판단축 — 「이 런타임은 확장을 무엇으로 싣는가」

오퍼레이터는 **제출·조정을 대행**할 뿐이고 **확장 적재는 런타임의 몫**이다.
그래서 굽는가/안 굽는가를 정하는 것은 오퍼레이터가 아니라 **런타임**이다.

| 확장 적재 방식 | 해당 | 전용 이미지 |
| --- | --- | --- |
| 클래스패스 jar — 이미지에 넣거나 런타임에 받거나, 둘뿐 | Spark · Flink | **필요** |
| operand 이미지 변형 — 업스트림이 조합해 배포 | PostgreSQL | 불필요 |
| 별도 컨테이너 플러그인(CNPG-I) | PostgreSQL(백업) | 불필요 |
| CR 필드 선언 — 롤·파라미터·스토리지 | PostgreSQL | 불필요 |

⇒ **JVM 클래스패스에 실려야만 하는 확장을 쓰는 런타임만 굽는다.**
새 컴퓨트 엔진을 볼 때 이 표를 먼저 적용한다.

### 2. 3종 개요 비교 — 구조만, 값은 링크

| 축 | Spark | Flink | PostgreSQL |
| --- | --- | --- | --- |
| 오퍼레이터 | `apache/spark-kubernetes-operator` | `apache/flink-kubernetes-operator` | CloudNativePG(CNCF) |
| 설치 주체 | `terraform/lakehouse-platform/` | 같음(값 파일 동반) | 같음 |
| CRD 그룹 | `spark.apache.org` | `flink.apache.org` | `postgresql.cnpg.io` |
| 주 kind | `SparkApplication` | `FlinkDeployment` | `Cluster` · `Database` |
| 워크로드 수명 | 배치 잡 = 일시 | 세션 클러스터 = JM 상주 | 영구 상주 |
| 전용 이미지 | **O** | **O** | **X** |
| 베이스 계열 | `apache/spark` | `flink` | CNPG operand |

**세 줄 단서** — 표만 보면 어긋나는 지점이다.

- **네임스페이스는 Terraform이 만들지 않는다.** 세 릴리스 모두 `create_namespace = false`이고
  `scripts/k8s-operators.sh`가 미리 만드는 **계약**이다. cert-manager와 Barman Cloud 플러그인은
  원격 멀티도큐먼트 매니페스트라 `helm_release`로 받지 못해 셸에 남는다([terraform.md](terraform.md)).
- **Spark Connect는 오퍼레이터 워크로드가 아니다.** 상시 SQL 엔드포인트는 `SparkApplication`이
  아니라 **평범한 Deployment**이고, 다만 **같은 러너 이미지**를 쓴다. 그래서 굽는 이유는
  공유하지만 수명·회수 다이얼은 다르다([spark.md](spark.md) §Spark Connect).
- **PostgreSQL 쪽 kind는 둘이 더 있다** — 백업은 `barmancloud.cnpg.io`의 `ObjectStore`와
  `ScheduledBackup`으로 선언한다. 이것이 아래 §3-C의 "별도 컨테이너 플러그인" 축이다.

### 3. 굽는 이유 — 나열이 아니라 분류

**대안이 있는데 기각한 것**과 **대안이 원리적으로 없는 것**을 가른다.
가르지 않으면 Flink가 Spark보다 **한 단 센 이유**가 표에서 사라진다.

#### A. 대안은 있으나 기각했다 (Spark · Flink 공통)

| 이유 | 내용 |
| --- | --- |
| 베이스에 없다 | Iceberg 런타임·AWS 번들·JDBC 드라이버가 베이스 이미지에 들어 있지 않다 |
| 네트워크 의존 | 런타임 의존성 해석은 **파드 기동마다** 외부 저장소를 탄다 |
| 버전 드리프트 | 해석 시점마다 결과가 달라질 수 있어 재현이 깨진다 |
| 짝이 추측 대상이 아니다 | S3A jar은 **베이스의 Hadoop 클라이언트와 같은 버전**이어야 하고, SDK 번들 버전도 pom이 정한다 |
| 같은 jar 세트 | driver·executor·상시 SQL 엔드포인트가 **한 벌**을 봐야 한다(Spark) |
| 진입점 배치 | `spark-submit`이 `local://` 진입점을 CWD로 복사하며 **대상을 먼저 지운다** — 이미지 안 경로가 그래서 정해진다(Spark) |

⇒ 전부 **재현성 축**이다. 굽는 것은 그 축을 이미지 레이어에 박제하는 수단이다.

#### B. 🔴 대안이 원리적으로 없다 (Flink 전용)

**Flink는 A에 더해 세 가지가 붙는다. 셋 다 "네트워크를 쓰면 되지 않나"로 풀리지 않는다.**

1. **Hadoop 클래스가 Flink 이미지에 아예 없다.** Iceberg 카탈로그 팩토리가 Hadoop
   `Configuration`을 로드하므로 `CREATE CATALOG` 단계에서 죽는다.
   **Spark 이미지와 갈리는 지점이고**, 이것이 Flink 러너에 shaded Hadoop 클라이언트를
   넣는 이유다([../conventions/k8s.md](../conventions/k8s.md) §9-2).
2. **S3 파일시스템 플러그인은 "받는" 문제가 아니라 "옮기는" 문제다.**
   베이스 이미지가 그 jar을 **이미 갖고 있는데** Flink는 `opt/`의 jar을 자동으로 올리지 않는다.
   게다가 `lib/`가 아니라 **`plugins/<이름>/`** 이어야 한다 — 그 jar이 AWS SDK v1을
   재배치 없이 품고 있어 SDK v2와 같은 클래스로더에서 충돌하고, Flink 플러그인 규약의
   **격리 클래스로더**만이 그 충돌을 없앤다.
   ⇒ **다운로드가 0인데도 이미지 레이어가 필요하다.** 네트워크 문제가 아니라 **파일 배치**
   문제라 런타임 대안이 존재하지 않는다.
3. **오퍼레이터가 "안 굽는 길"을 정책으로 닫았다.** jar 아티팩트 허용 스킴 기본값이
   원격뿐이라 이미지 동봉 jar이 웹훅에서 거부된다. 이 저장소는 값을 뒤집어
   **로컬만 허용하고 원격을 뺐다** — 남겨두면 CR 한 줄로 **런타임 외부 jar fetch 경로**가
   열리기 때문이다(공급망). ⇒ **여기서는 굽는 것이 곧 통제다.**

⚠️ 3의 통제는 **값 파일에 얹혀 있다** — Flink 릴리스만 `--set`과 값 파일을 함께 쓰고,
파일을 빠뜨리면 그 통제가 **조용히 풀린다**(`terraform/lakehouse-platform/operators.tf` 주석).

#### C. PostgreSQL이 안 굽는 이유

| 축 | 내용 |
| --- | --- |
| operand 카탈로그 | 업스트림이 이미지 **변형(TYPE)** 을 조합해 배포한다 — 고르는 문제이지 굽는 문제가 아니다 |
| 백업이 밖에 있다 | in-tree가 아니라 **CNPG-I 플러그인(별도 컨테이너)** 이라 DB 이미지에 백업 바이너리가 필요 없다 → 더 가벼운 변형을 고를 수 있었다 |
| CR이 흡수한다 | 부트스트랩·관리 롤·서버 파라미터·스토리지·자원이 전부 필드 선언이다 |

⇒ **구울 유일한 조건**: operand 카탈로그에 없는 확장이 필요해질 때.
현재 카탈로그 DB는 테이블 메타만 담아 해당하지 않는다.

### 4. 굽지 않는 대안과 탈락 사유

| 대안 | 탈락 사유 |
| --- | --- |
| 런타임 의존성 해석 | 파드 기동마다 네트워크를 타고 버전이 드리프트한다(§3-A) |
| PVC·initContainer 주입 | 오브젝트가 늘고, jar 세트의 단일 출처가 이미지 밖으로 나간다 |
| 오브젝트 스토어에서 fetch | **부트스트랩 역설** — S3 접근용 jar을 받으려면 S3 접근이 이미 있어야 한다 |
| 전용 이미지(현행) | 채택. 버전 짝을 레이어에 박제하고, Flink에서는 공급망 통제까지 겸한다 |

### 5. 🔴 「차트 버전」과 「오퍼레이터 버전」은 다른 수다 — 3종 공통 축

오퍼레이터마다 버전이 **둘**이다 — 설치에 주는 **차트 버전**과 그 차트가 깔아 주는
**오퍼레이터(app) 버전**. 「핀 버전」이라는 한 낱말로 세 축을 한 표에 적으면
**값은 각각 맞는데 단위가 어긋난 표**가 나온다.

| 축 | 두 수의 관계 | app 버전이 적힌 자리 |
| --- | --- | --- |
| Spark | **다르다** | 변수 블록 위 주석 |
| Flink | **같다** | 변수의 `description` 문자열 |
| PostgreSQL | **다르다** | 변수 블록 위 주석 |

**"셋 다 다르다"로 외우면 틀린다.** 같은 축이 하나 섞여 있다는 것이 이 함정의 핵심이고,
그래서 규칙이 아니라 **매번 확인**이 답이다.

#### 갈리는 축은 「무엇이 검증하나」다

- `chart_version`은 **타입 있는 필드**라 `terraform validate`의 대상이다.
- 짝이 되는 app 버전은 **셋 다 산문**이다(주석 둘 + `description` 하나).
  **`terraform validate`도 린터도 주석과 `description`을 검증하지 않는다.**
- 그런데 둘은 **같은 변수 블록, 같은 시각적 단위** 안에 붙어 있다 —
  **찾기는 쉬운데 기계가 보지 않는 자리에 짝이 있다.**

#### 파생 실패 모드는 둘이고, 가역성이 갈린다

**ⓐ 읽는 쪽이 단위를 혼동한다 — 실제로 일어났다.**
📌 이 문서를 쓰게 한 비교표가 바로 그 혼동을 담고 있었다 — 한 「핀」 열에 차트 버전과
app 버전이 섞였고, **값이 각각 맞았기 때문에 검산을 통과했다.**
원인은 부주의가 아니라 **선언 구조**다: 검증되는 필드와 검증되지 않는 산문이 같은
블록에 나란히 있으면 읽는 쪽이 둘을 한 칸에 담는다.

**ⓑ 쓰는 쪽이 한쪽만 갱신한다 — 감지 수단이 없다.**
`chart_version`은 타입 필드라 바꿀 때 눈에 띄지만, 짝인 산문은 **안 고쳐도 아무것도
깨지지 않는다.** 필드는 갱신되고 산문은 남아 **짝이 조용히 거짓이 되고**, 그 거짓 짝이
다음 사람이 *"근거가 있다"* 고 믿는 문장이 된다([../philosophy.md](../philosophy.md) 원칙 7).

**ⓑ의 등급은 `미확인`이 아니다 — 단위를 갈라야 나온다**([../risk.md](../risk.md)).

| 무엇을 세나 | 관측 | 판정 |
| --- | --- | --- |
| **메커니즘** — 산문이 이관·변경을 못 따라온다 | **3건**(핀 위치를 가리키던 규약 문장 둘 + 변수 파일 헤더 자신) | **실증됨** · Rule of Three에 닿는다 |
| **ⓑ 자체** — chart↔app **짝**이 거짓이 된다 | **0건** — 현재 세 짝은 정합 | 이 축에서는 **미발생** |

⚠️ **세 번째 사례가 하필 그 짝 산문을 담고 있는 파일의 헤더다.** 핀 정본이 셸에서
Terraform으로 옮겨갈 때 한쪽 산문만 갱신돼, 두 파일이 **서로를 정본이라고 가리키는**
상태가 됐다. 같은 파일에서 산문이 이미 한 번 낡았으므로
**「이 축은 깨끗하다」를 안심으로 읽지 않는다.**

**이 실패는 층을 가리지 않는다** — 선언 파일 안이든, 비교표의 한 칸이든, 사례를 세는
일이든 같은 모양으로 온다. 공통점은 **값이 맞다는 것**이고, 그래서 검산을 통과한다.

**가역성은 갈라 적는다** — 이 저장소는 영향×가능성에 **가역성**을 더한다.

| 대상 | 가역성 |
| --- | --- |
| 드리프트 자체 | **가역** — 문장 한 줄이다 |
| 그 거짓 짝을 인용한 결정 | **그 결정의 가역성을 따른다** — 「이 차트가 저 app을 싣는다」를 믿고 돌린 업그레이드의 되돌림 비용은 문장 수정과 같지 않다 |

⚠️ **산문이 말하는 app 버전은 저장소의 주장**이다. 외부 1차 출처로 확인된 값이 아니므로
이 문서도 그것을 확정 사실로 다루지 않는다 — 판정이 필요하면 상류 릴리스에서 대조한다.

- **핀의 정본은 `terraform/lakehouse-platform/variables.tf`** 의 각 변수
  `default.chart_version`이다. 오퍼레이터 설정은 셸에서 그쪽으로 이관됐고,
  셸에 남은 `*_VERSION`은 cert-manager·ingress·백업 플러그인이지 **오퍼레이터 차트가 아니다.**
- **Flink 차트는 저장소 URL 자체에 버전이 박힌다.** 상류가 현행 릴리스만 보관해
  **구버전 URL이 404가 되고 설치가 깨진다** — 버전을 올릴 때 URL도 함께 움직인다.

## 운영 메모

### 공통 규율

- **오퍼레이터 이미지와 차트는 공식 배포판 그대로 쓴다** — 굽는 것은 잡 런타임뿐이다.
- **러너 이미지 태그는 구체 버전 고정**이다. 가변 채널 태그는 `pullPolicy: Always`와 만나
  **같은 태그가 다른 내용을 가리키는 드리프트**를 만든다
  ([../conventions/docker.md](../conventions/docker.md) §1-3).
- **태그를 올렸으면 그 태그를 참조하는 매니페스트를 함께 올린다** — 한쪽만 올리면 구 이미지가
  계속 돈다([../conventions/k8s.md](../conventions/k8s.md) §10).
- **러너 이미지는 로컬 레지스트리에 직접 push**한다. 호스트와 클러스터가 같은 이름을 쓰도록
  배선돼 있어 별도 적재 단계가 없다(같은 §10).
- **버전 핀이 두 곳이 되지 않게 한다** — 베이스 이미지가 자기 버전으로 넣는 파일은
  베이스 태그가 유일한 핀이다. 빌드 인자로 다시 적으면 한쪽만 올렸을 때 조용히 깨진다.

### 🔴 세 축이 공유하는 실패 모드 — "성공한 것처럼 보이는데 안 된 상태"

이것이 [../philosophy.md](../philosophy.md) 원칙 7이 오퍼레이터 축에 나타나는 형태다.
셋 다 **한 번씩 만들었다** — 패턴이 같으니 다음 축에서도 같은 모양으로 온다.

| 축 | 어떤 모양이었나 | 상세 |
| --- | --- | --- |
| Spark | 잡은 성공하고 데이터도 들어갔는데 **오케스트레이터만 몰랐다** | [../conventions/k8s.md](../conventions/k8s.md) §9 |
| Flink | **DDL·조회는 통과하고 쿼리 실행만** 권한 오류로 갈렸다 | 같은 문서 §9-2 |
| PostgreSQL | **시크릿만 회전되고 DB 롤은 그대로**였다 | [../conventions/k8s/cnpg.md](../conventions/k8s/cnpg.md) |

⇒ 공통점은 **부분 성공**이다. 정상 경로 하나가 통과하는 것을 전체 통과로 읽으면 잡히지 않는다.
새 배선을 걸면 **일부러 위반시켜** 막히는지 본다.

### 재검토 트리거 — 시점이 아니라 조건

- **엔진 버전을 올릴 때** — 🔴 **최신이 아니라 Iceberg가 지원하는 짝**을 고른다.
  런타임 아티팩트의 실재를 1차 출처로 확인하고 정한다([spark.md](spark.md) §버전 선택 규칙).
- **operand 카탈로그에 없는 PostgreSQL 확장이 필요해질 때** — 그때 PostgreSQL도
  §1 표에서 굽는 축으로 넘어간다. 그 전에는 넘어가지 않는다.
- **오퍼레이터를 갈아끼울 때** — 매니페스트·스크립트뿐 아니라 **상태 판정 글루 코드까지**
  함께 옮긴다. 이전 때 누락돼 자산이 죽어 있던 전례가 있다.
- **새 컴퓨트 엔진을 도입할 때** — §1 판단축을 **먼저** 적용해 굽는 축인지 판정한다.
  굽는 축이면 §3-A의 여섯 이유가 그대로 따라온다.
- **`chart_version`을 바꿀 때** — 같은 변수 블록의 산문(주석·`description`)이 말하는
  app 버전 짝을 **함께** 본다. §5-ⓑ의 드리프트는 **감지 수단이 없어** 이 조건이
  유일한 관문이다. 수용한 리스크이므로 근거와 함께 트리거를 여기 남긴다.
- **오퍼레이터 값 파일·허용 스킴을 손댈 때** — §3-B의 3은 공급망 통제라 자원·성능 축의
  변경과 같은 무게로 다루지 않는다.
