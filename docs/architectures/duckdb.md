# DuckDB (아키텍처 · 프로젝트 관점)

## 개요

DuckDB는 **인프로세스(in-process) 분석용 OLAP 데이터베이스**다. 서버를 따로 띄우지 않고
호스트 프로세스에 라이브러리로 링크돼, 같은 메모리 공간에서 열 지향 벡터화 실행으로 SQL을 처리한다.
SQLite가 OLTP에서 차지하는 자리를 OLAP에서 차지하는 설계다.

파일을 테이블처럼 직접 읽는 것이 특징이다 — 로컬 csv·parquet을 적재 단계 없이 `FROM`에 바로 놓고
질의할 수 있고, 자체 파일 포맷 하나로 영속화도 된다. 즉 **엔진 기동·카탈로그 등록·네트워크 왕복이
전부 없는 대신, 데이터가 한 대의 머신에 들어와 있어야** 성립한다.

## 이 프로젝트에서의 위치 — 🔎 미채택 (선언 잔존 · 실행 경로 없음)

**상태 마커 근거**: 이 저장소는 DuckDB를 **한 번도 배선한 적이 없는데 문서에는 남아 있다.**
[monitoring.md](monitoring.md)의 잔존과는 성격이 다르다 — 그쪽은 정의도 있고 켜면 실제로 돌지만
보고 있는 대상이 정본이 아니다. 이쪽은 **켤 것 자체가 없다.**
그래서 🔎 미채택 + **"선언은 남아 있고 실행 경로가 없다"** 로 표기한다.

### 현행 사실 — 어느 축에도 실체가 없다

축의 **이름으로** 적는다(파일·줄 번호와 실측 수치는 저절로 낡으므로 두지 않는다 —
[../doc-sync.md](../doc-sync.md) 실무 규칙).

| 실행 경로가 성립하려면 필요한 것 | 현황 |
| --- | --- |
| **런타임 의존성**(`pyproject.toml`·`uv.lock`) | 없다 — `uv run`으로도 CLI로도 불러낼 대상이 프로젝트에 없다 |
| **스킬 등재**(`skills-lock.json`) | 없다 |
| **워커 배선**(`analyst` 지시문 §참고 스킬) | 없다 — 승격 심사에서 **죽은 참조로 제거**됐다([../skills.md](../skills.md)) |
| **조회 엔진 정본**([../conventions/analysis.md](../conventions/analysis.md) §6) | Spark Connect다 |
| **도구 표의 서술** | 쓸 수 있는 도구로 적혀 있었다 ← **이 문서가 해소하는 드리프트** |

⚠️ 위는 **저장소 파일 기준**이다. 개인 개발 환경에 DuckDB CLI가 깔려 있는지 여부는 별개 축이고
이 문서의 판단에 들어가지 않는다 — 저장소가 재현을 보증하는 범위 밖이다.

⚠️ [../skills/caveats.md](../skills/caveats.md)·[../skills/sourcing.md](../skills/sourcing.md)에
DuckDB 항목이 남아 있는 것은 **활성 배선이 아니라 강등 근거의 보존**이다
([../skills/scoring.md](../skills/scoring.md)가 그렇게 명시한다). 근거를 지우면 다음 심사가
같은 판단을 처음부터 다시 하게 되므로 남긴다 — **"기록이 있다"를 "쓰고 있다"로 읽지 않는다.**

### 왜 매력적인가

미채택 이유를 적기 전에 매력을 먼저 적는다. 그래야 다음에 같은 제안이 올라왔을 때
**이미 저울에 올렸던 것**임이 드러난다.

- **상주 자원이 0이다.** 이 저장소의 자원 규약은 상주 컴퓨트를 가장 비싼 선택으로 본다
  ([../resource-sizing.md](../resource-sizing.md)). 인프로세스 엔진은 그 축에서 유일하게 공짜다.
- **기동 대기가 없다.** Spark Connect는 서버가 떠 있어야 하고 executor 파드가 함께 산다.
  파일 한 개를 세어 보려고 클러스터 상태를 확인하는 왕복이 사라진다.
- **소형 csv·parquet에 즉시 붙는다.** 적재·카탈로그 등록 없이 파일 경로만으로 질의가 된다.

### 왜 그럼에도 쓰지 않는가

| 축 | 내용 |
| --- | --- |
| **조회 엔진 정본이 하나다** | 정본은 **Spark Connect**다([../conventions/analysis.md](../conventions/analysis.md) §6). 엔진이 둘이면 같은 SQL이 다른 값을 낼 여지가 생기고, 이 저장소는 이미 `dbt.datediff`에서 그 사고를 한 번 겪었다 |
| **결론 수치의 경유 경로가 정해져 있다** | 결론에 쓰는 수치는 **gold/dbt 모델을 경유**한다. 임시 엔진의 결과가 리포트에 들어가는 순간 재현 경로가 끊긴다 — 도구가 규약을 어기게 만드는 것이 아니라 **어기기 쉽게** 만드는 것이 문제다 |
| **로컬 파일 내보내기는 보안 축이다** | 행 단위 데이터를 로컬 파일로 떨구는 경로가 열린다. 판정 정본은 [../security.md](../security.md)이고 여기에 내용을 복제하지 않는다 |
| **먹일 것이 지금 없다** | 소형 로컬 파일 즉석 탐색이 **반복 작업으로 나타난 적이 없다**. 도구를 먼저 두고 용도를 찾는 순서를 이 저장소는 [monitoring.md](monitoring.md)에서 이미 한 번 거부했다 |

⇒ 기각 사유의 무게 중심은 **자원 비용이 아니다.** DuckDB는 자원 축에서는 오히려 최상위이고,
걸리는 곳은 **단일 출처(정본 엔진·결론 경유 경로)와 반출 경로**다.

## 운영 메모

- **재검토 트리거는 시점이 아니라 조건이다.** 소형 csv·parquet의 즉석 탐색이
  **3회 이상 반복되면**(Rule of Three — [../philosophy.md](../philosophy.md)) 의존성 추가와
  스킬 재등재를 재검토한다. 한 번의 불편은 트리거가 아니다.
- 🔴 **재등재는 공급망 행위다.** 스킬 등재·`skills-lock.json` 편집은 외부 코드를 실행 컨텍스트에
  주입하는 것이라 **`security` 검토**를 거친다([../skills.md](../skills.md)).
  의존성 추가와 스킬 재등재는 **다른 축**이고, 한쪽이 통과했다고 다른 쪽이 열리지 않는다.
- 🔴 **재검토가 열리면 반출 경로를 먼저 본다.** 자원 산정이 아니라
  [../security.md](../security.md) 판정이 선결 조건이다 — 이 저장소는 DUA가 걸린 데이터를 다루고,
  인프로세스 엔진의 편의성은 곧 **파일로 떨구기 쉽다**는 뜻이기도 하다.
- **도구 표에서 행을 지우지 않는 이유**: 지우면 "왜 안 쓰는가"가 함께 사라져
  다음 사람이 같은 제안을 다시 올린다. 미채택은 **기록으로 남을 때만 결정**이다.
