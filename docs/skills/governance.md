# 스킬 통제 규칙

[`../skills.md`](../skills.md)가 「무엇에 쓰나」를 다룬다면, 이 문서는 **스킬을 어떻게 들이고 어떻게 다루나**를 다룬다.
각 규칙에는 그 규칙이 왜 필요한지 함께 적는다. 판정 경위와 실측 기록은 git 이력과 볼트(비공개)에 있다.

## 세 축 — 섞지 않는다

스킬은 아래 세 질문으로 따로 읽는다. 한 칸에 섞으면 한 축의 통과가 다른 축의 통과로 착각된다.

| 축 | 값 | 무엇을 묻나 |
| --- | --- | --- |
| **고정** | lock 등재 / lock 밖 / 런타임 제공 | 조용히 바뀔 수 있는가 |
| **출처 등급** | A / B / C / D(아래) | 누가 썼는가 |
| **설치 범위** | 프로젝트 / 전역 | 클론에 따라오는가 |

- **lock은 「안 바뀜」을 보장하지 「안전함」을 보장하지 않는다.** lock의 `computedHash`는 디렉터리 전체를 덮는다.
  그래서 재계산하면 변조를 **탐지할 수 있다**. 다만 재계산을 자동으로 돌리는 검사는 저장소에 없고,
  실행을 **차단**하지도 않는다. 개인 저장소 스킬도 lock에 넣는 순간 등재된다.
- **런타임 제공 스킬**(하네스·플러그인 내장)은 디스크에 파일이 없다.
  그래서 워커 지시문에 적어도 워커가 `Read`할 수 없다.
- **전역과 프로젝트에 같은 이름이 있으면 전역이 이긴다.** 그러면 프로젝트 사본이 조용히 죽는다.
  그래서 전역은 비우고 프로젝트 스코프만 쓴다.

## 출처 등급

등급은 출처 계정이 아니라 **스킬 단위**로 매긴다. 기준은 「그 스킬이 다루는 도구의 벤더가 썼는가」다.
그래서 같은 출처 안에서도 등급이 갈릴 수 있다. 문자열 규칙으로 자동 분류하면 틀리므로 사람이 읽고 판정한다.

| 등급 | 정의 | 다루는 법 |
| --- | --- | --- |
| **A** | 스킬이 다루는 도구 = 출처의 제품 | 제한 없이 사용 |
| **B** | 조직 계정이지만 그 도구의 벤더는 아님 | 사용 가능. 실행 파일이 있으면 보안 검토 |
| **C** | 개인·커뮤니티 계정 | 도입 전 보안 검토 필수 + 단서 필수. **실행 파일이 있으면 도입 금지**(예외는 §C등급 단서) |
| **D** | 출처를 알 수 없음 | 실행 파일이 있으면 검토 전 사용 금지, 문서뿐이면 관찰 |

**등급과 무관하게, 실행 파일(`scripts/` 등)을 포함한 스킬은 보안 검토 대상이다.** 마크다운은 제안이지만
스크립트는 실행이다. 어느 스킬에 실행 파일이 있는지는 문서에 박아 두지 않고 그때그때 센다.

```bash
find -L .claude/skills -type f \( -name '*.sh' -o -name '*.py' -o -name '*.js' -o -name '*.cjs' \
    -o -name '*.mjs' -o -name '*.ts' -o -perm -u+x \) | cut -d/ -f3 | sort | uniq -c
```

저장소 루트에서 돌린다. `.claude/skills/`는 gitignore 대상이라 새 worktree에는 없고,
그 자리에서 돌리면 빈 출력이 나온다(「실행 파일 0」이 아니라 「대상 없음」이다).
`scripts/` 디렉터리만 세면 안 된다. `hooks/` 같은 다른 자리에 둔 실행 파일이 빠진다.
`find -L`을 쓰는 이유는 `.claude/skills/` 안에 심볼릭 링크와 실디렉터리가 섞여 있어서다.
링크를 따라가지 않으면 절반만 센다.

## 설치·갱신·제거

- **설치·갱신은 스킬 CLI(`npx skills`)로만 한다.** CLI가 lock에 `source`와 `computedHash`를 기록한다.
  `skills-lock.json`은 손으로 고치지 않는다. `permissions.ask`에 `Edit(skills-lock.json)`이 있지만
  auto 모드에서는 파일 도구의 `ask`가 흡수되므로, 이 규칙은 기계 차단이 아니라 규율이다.
- **설치는 비가역 작업이다** — 네트워크에서 남의 코드를 받아 온다. 계획만 세운 뒤
  `reviewer` 보안 체크리스트를 거치고 사용자 승인을 받는다([risk.md](../risk.md) §4).
- **lock은 커밋한다.** `.agents/`·`.claude/skills/`는 gitignore 대상이라,
  클론에서 같은 스킬을 재현하는 근거는 lock 하나뿐이다.
- **lock에 있다고 다시 받을 수 있는 것은 아니다.** 업스트림에서 스킬이 사라지면 다른 머신에서는 복원되지 않는다.
- **`npx skills remove -g`는 전역에만 머물지 않는다.** 이름이 같은 프로젝트 스킬까지 함께 지운 적이 있다.
  그래서 제거 전후로 두 스코프를 모두 센다. 링크형 레이아웃을 백업할 때는 `tar -h`를 쓴다.
- 스킬을 추가·제거하면 [`../skills.md`](../skills.md) 표도 같은 PR에서 고친다(대조 스니펫이 그 문서에 있다).

## 워커에 스킬을 물리는 방법

| 경로 | 수단 | 뜻 |
| --- | --- | --- |
| 프리로드 | 프론트매터 `skills:` | 기동할 때 `SKILL.md` 본문이 컨텍스트에 들어간다 |
| 온디맨드 | `tools:`에 `Skill` | 워커가 필요할 때 호출한다 |
| 차단 | `Skill` 생략 또는 `disallowedTools: Skill` | 호출 자체를 막는다 |

- **`skills:`는 화이트리스트가 아니라 프리로드다.** 접근을 막는 축은 `tools:`/`disallowedTools`뿐이다.
- `Skill` 도구는 설치된 **모든** 스킬에 닿는다. lock 밖 하네스 스킬(`update-config` 등)도 포함된다.
  그래서 워커 지시문의 §참고 스킬 표는 **규율**이고 기계 강제는 없다. 워커별 매핑의 정본은 그 표다.
- **단, 지시문이 정본인 범위는 「어느 워커에 무엇을 물리나」까지다.** 출처 등급·C등급 통제·프리로드 자격·lock 관리는
  이 문서가 정본이고, 지시문을 고친다고 바뀌지 않는다. 범위를 열어 두면 지시문 편집만으로 C등급 통제를 건너뛸 수 있다.

**표에 올리는 기준(등재 루브릭).** 먼저 게이트 2축을 통과해야 한다. 하나라도 걸리면 채점하지 않는다.
단서로 무해화할 수 있으면 통과로 본다.

1. **권한 정합**: 스킬 절차가 그 워커의 권한(커밋 금지·계획만 반환 등)과 충돌하지 않는다.
2. **정본 무충돌**: 스킬 절차가 저장소 정본 규약과 충돌하지 않는다.

통과한 스킬만 채점 3축(스택 일치 · 호출 빈도 · 대체 불가)으로 매긴다. **★3, 즉 세 축을 모두 만족하는 것만 등재**한다.
출처 신뢰성은 별점에 넣지 않는 별개 게이트다(보안 검토). ★3이어도 보안 검토를 거치지 않았으면 등재하지 않는다.

**프리로드 자격 = lock 등재 ∧ 보안 검토 완료 ∧ 상시성.** 상시성은 그 워커의 거의 모든 배정에서
스킬 발동 조건이 참이라는 뜻이다. 세 조건은 모두 거부권이고 AND다. 점수로 상계하지 않는다.
상시성이 필요한 이유는 비용이다. 프리로드한 본문은 배정마다 **무조건** 컨텍스트에 들어간다.
그래서 발동률이 낮은 스킬은 필요할 때 `Skill`로 부르는 편이 싸다.

**`skills:`에 없는 이름을 적어도 에러가 나지 않는다.** 워커는 정상 기동하고 그럴듯하게 답한다.
경고는 `--debug-file` 로그에만 남는다. 그래서 `skills:`에 이름을 추가하거나 스킬을 제거할 때는
`--debug-file` 로그에서 `Preloaded skill '<이름>'` 한 줄이 찍히는지 확인한다.

## C등급 단서

**원칙: C등급 + 실행 파일 = 도입 금지다.** 예외는 「분리안」 하나다.
마크다운 절차만 참조하고 실행 파일은 실행하지 않는 방식이다. 분리안은 아래 두 조건을 **모두** 갖춘 스킬에만 적용한다.

1. 사용자가 그 스킬에 대해 개별로 결정했다.
2. 실행 경로를 막는 강제 수단(`permissions.deny`)이 있다.

예외는 C등급 금지의 근거(「스크립트는 실행이다」)를 범위에서 빼는 **적용 범위 해석**이다. 새 등급 규칙이 아니다.
분리안에서는 실행 경로만 끊고 파일은 디스크에 남긴다.
파일을 지우면 lock 해시와 영구히 어긋나 진짜 변조와 구분할 수 없게 된다.

| 대상 | 단서 | 강제 수단 |
| --- | --- | --- |
| `brainstorming` | 분리안 — `scripts/`(브라우저 동반 서버) 실행 금지 | `permissions.deny`의 `Bash(*brainstorming/scripts*)` |
| 실행 파일이 있는 그 밖의 obra/superpowers | 위 두 조건이 없어 **원칙(도입 금지)과 어긋난 상태다** | 없음 — 처리 방향은 Issue로 추적한다 |
| mattpocock/skills(`grilling`·`grill-me`) | 실행 파일 없음. 질의 절차만 참조한다 | 해당 없음 |
| obra/superpowers 전반 | 「설계 문서를 커밋하라」, `docs/superpowers/` 산출 경로 | 따르지 않는다. 커밋은 사용자 요청 시에만 한다 |
| obra/superpowers 전반 | 존재하지 않는 후속 스킬 호출 지시 | 없는 스킬이면 건너뛰고 사용자에게 알린다 |

`Bash(*brainstorming/scripts*)` 규칙에는 부수 효과가 있다.
이 문자열이 들어간 **모든** Bash 명령이 막히고, 문서 grep도 예외가 아니다.
`Read`·`Grep` 도구는 영향을 받지 않는다.

## 워크플로 발신 공백 (G-1)

스킬이 CI 워크플로 템플릿을 제안할 때 주의할 공백이다. 에이전트가 워크플로 **파일을 쓰고**,
실행은 **나중에 CI 러너가** 한다. 에이전트의 `Bash` 명령만 보는 `permissions`는 원리상 이 경로를 볼 수 없다.

- **결정**: `.github/workflows/**`는 `devops-engineer` 단독 소유로 둔다. 배포·발신 스텝이 들어가는 편집이면
  그 워커는 **계획만 반환**한다. `Edit(.github/workflows/**)` deny는 쓰지 않는다.
  정당한 CI 편집까지 막아 우회 습관만 만들기 때문이다.
- **배포·발신 스텝 5종**(`devops-engineer` 지시문과 한 벌):
  레지스트리 push · 위키 push · 릴리스 생성 · `kubectl apply` · `terraform apply`.
- **한계**: 이 결정은 지시문 규율이라 기계로 강제되지 않는다.
  지금 에이전트가 **직접** 발화하는 경로(`gh workflow run` 등)에는 `permissions.ask` 규칙이 있다.
  다만 ask가 실제로 멈추는지는 규칙과 auto 모드 분류기에 함께 달려 있어, 「규칙이 있다」가 「반드시 멈춘다」는 아니다.
  시차를 두고 실행되는 공백 자체는 닫히지 않았다.
