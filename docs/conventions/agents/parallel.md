# 병렬 세션 (session sync)

> 에이전트 규약 인덱스는 [`../agents.md`](../agents.md).
> 세션 간 협업 규율은 [`peer.md`](peer.md), worktree 생성은 [`../git.md`](../git.md) §7.

병렬 세션은 **서로를 모른다.** 그래서 점유 사실을 **파일시스템에 남기고** 다음 세션에게 보여준다.
구현은 [`session_sync_guard.py`](../../../scripts/session_sync_guard.py),
레지스트리는 `.claude/.claims/`(**gitignore** — 머신 로컬 런타임 상태).

## 감지 축

| 축 | 판정 키 | 충돌 시 |
| --- | --- | --- |
| **서브에이전트 중복** | `subagent_type` + 대상 지문 Jaccard ≥ 0.5 | 실행 중 → `ask` / 완료 → 결과 요약 주입 |
| **동일 파일 동시편집** | 파일 절대경로 | 다른 세션 리스가 20분 내면 `ask` |
| **워킹트리 전역 변경** | 전역 git 명령 + 살아 있는 다른 세션 유무 | 다른 세션이 있으면 `ask` |

앞의 둘은 "무엇을 건드리는가"를 보지만 전역 변경은 **대상이 전부**라 비교할 게 없다 —
대신 **"지금 이 워킹트리에 나 말고 누가 있나"** 를 묻는다. 그래서 각 세션은 어떤 hook이 돌든
`sessions/<ref>.json`에 **생존 신호**(TTL 90분)를 먼저 남긴다. 파일 리스·claim은 *작업을 해야*
생기는데, 전역 변경은 **아직 아무것도 안 한 세션에게도 피해를 주기** 때문이다.

- **차단이 아니라 소통이다.** 판정이 휴리스틱이라 오탐이 나므로 `deny`가 아니라 `ask`로 올린다.
- 이미 **끝난** 작업은 막지 않고 결과 요약을 컨텍스트로 흘린다 —
  목적은 봉쇄가 아니라 **재호출 대신 재사용**이다.
- 리스 **획득은 `PostToolUse`** 가 한다. 승인·성공한 편집에서만 발동하므로
  리스가 "고치려던 사람"이 아니라 **"실제로 고친 사람"** 을 가리킨다.

## TTL

| 대상 | 수명 | 근거 |
| --- | --- | --- |
| 실행 중 claim | 30분 | 초과분은 죽은 세션의 잔해 |
| 완료 claim | 6시간 | 이후엔 데이터가 변했을 수 있어 재사용이 위험 |
| 파일 리스 | 20분 | 편집마다 갱신되므로 "최근 손댄 흔적"에 가깝다 |

`SessionEnd`가 내 리스·실행 중 claim을 회수하고 **완료 claim은 남긴다**(다음 세션의 재사용분).
세션이 비정상 종료해도 TTL이 회수한다.

## hook 결정값

`PreToolUse` hook의 `permissionDecision` **유효 값은 네 개뿐**이다.

| 값 | 뜻 | 비고 |
| --- | --- | --- |
| `allow` | 확인 없이 통과 | |
| `deny` | 차단 | **auto 모드에서도 집행된다** |
| `ask` | 사용자 확인 | auto 모드에서는 분류기가 흡수할 수 있다 |
| `defer` | 판단 보류 | **print-mode 전용** — 대화형 세션에서는 무시된다 |

🔴 **목록 밖의 값을 쓰면 출력 객체 전체가 거부되고 도구가 그냥 진행한다**(fail-open).
`hookSpecificOutput`이 discriminated union이라 값 하나가 어긋나면 그 hook의 결정이 통째로 폐기된다.
증상은 세션당 한 번 뜨는 검증 실패 배너뿐이고 **그 뒤로는 아무 일도 일어나지 않는다.**

### `ask`는 하드 스톱이 아니다

auto 모드(`classifyAllShell`)에서는 **분류기가 먼저 판정**하고 hook의 `ask`도 그 흐름에서 해소된다.
분류기가 무해하다고 본 호출은 사람에게 올라오지 않는다.

**흡수 여부는 도구 축에 따라 갈린다.**

| 축 | 결과 |
| --- | --- |
| `Bash` — 실제 위험 호출 | **발동한다** |
| `Bash` — 무해 호출 | 흡수 |
| **파일 도구**(`Edit`·`Write`·`NotebookEdit`) | **경로 민감도와 무관하게 흡수** |

⇒ **급소는 "경로가 민감한가"가 아니라 "어느 도구인가"이고, 파일 경로 경계는 `deny`여야 막힌다.**

- **`ask` 규칙이 있다는 사실을 "반드시 멈춘다"로 읽지 않는다.**
  멈추는 것은 **규칙 × 분류기 판정**의 곱이다.
- **`ask`의 실효는 직접 검증할 수 없다** — 프로브가 위험해야 프롬프트가 뜨는데 위험하면 실행할 수 없고,
  안전한 프로브는 그 안전함이 곧 분류기가 삼키는 조건이 된다.
  임시 `deny` 전환으로만 **간접 확인**하고, 확인이 끝나면 `ask`로 되돌린다.
- 비가역 명령은 **`ask` + 워커 지시문 금지 조항의 이중 방어**로 둔다.
  **어느 쪽도 단독으로는 봉쇄가 아니다.**

### 차단 문구의 출처로 구분한다

가드가 막으면 `permissionDecisionReason` **원문**이, 분류기가 막으면
`denied by the Claude Code auto mode classifier`가 나온다.
이 구분을 안 하면 **"막혔으니 내 가드가 작동한다"로 오독**한다.

### 반영 시점

| 설정 | 반영 | 검증 |
| --- | --- | --- |
| `permissions`(`settings.json`) | **세션 도중 즉시** | 고친 세션에서 바로 대조 |
| 프론트매터 `hooks`의 **배선** | **정의 로드 시점 스냅샷** | **새 세션**에서 3셀 대조 |
| 가드 **스크립트 본문** | **매 호출 시 즉시** | 고친 세션에서 바로 대조 |

🔴 **둘을 "설정 파일"로 묶어 같은 규칙으로 기억하면 틀린다.** `hooks` 배선을 고치고
같은 세션의 음성 결과를 근거로 삼으면 **판정 자체가 무효**다.

## matcher가 걸려도 경로 키가 다르면 조용히 무시된다

`Edit`·`Write`는 경로가 `file_path`인데 **`NotebookEdit`은 `notebook_path`** 다.
가드가 한 키만 읽으면 matcher는 발동하는데 **핸들러가 대상을 못 찾아 no-op이 된다** —
에러가 아니라서 "가드가 걸려 있다"는 인상만 남는다.

🔴 **함정의 성립 조건은 둘이고, 둘 다 있어야 터진다.**

1. matcher가 **여러 도구에 걸치고**,
2. 그 도구들 사이에서 **이름이 갈리는 필드**를 읽는다.

단일 도구 matcher는 조건 1이 없어 애초에 터지지 않는다.
현행 가드가 읽는 키는 경로 3종(`file_path`·`notebook_path`·`path`)과 `command`·`Agent` 계열뿐이다.

- **가드를 고쳤으면 고친 도구와 원래 되던 도구를 둘 다 다시 친다.**
  고친 쪽만 확인하면 회귀를 못 본다.

  | 도구 | 수정 전 | 수정 후 |
  | --- | --- | --- |
  | `Write`(`file_path`) | ○ | ○ ← **회귀 없음을 여기서 본다** |
  | `NotebookEdit`(`notebook_path`) | ✕ | ○ ← 수정 실효 |

  **우상단 칸을 빼먹기 쉽다** — "새 경로가 열렸다"와 "기존 경로가 그대로다"는 다른 주장이다.
- **가드가 여럿이라고 "하나가 막으니 다 막힌다"고 읽지 않는다.**

**가드가 *내용*을 읽기 시작하면 이 함정이 되살아난다.** 내용 필드는 셋 다 다르다.

| 도구 | 내용이 담기는 키 |
| --- | --- |
| `Write` | `content` |
| `Edit` | `new_string` (+`old_string`) |
| `NotebookEdit` | **`new_source`** |

새 가드를 걸 때는 먼저 **matcher가 걸치는 도구 수 × 읽는 필드의 키 이름**을 표로 적고 시작한다.

## 상대 세션을 무엇으로 지목하는가

가드가 "다른 세션이 이 파일을 만졌다"고 알려줘도 **그 세션을 특정하지 못하면 반쪽짜리**다.

| 식별자 | hook이 읽을 수 있는가 | `ListAgents` 대응 | 판정 |
| --- | --- | --- | --- |
| `TMUX_PANE` | ✅ 환경변수 | `tmux 0:@0.%4` 컬럼 | ✅ **전역 일치** |
| `CLAUDE_PID` | ✅ 환경변수 | 소켓 이름 | ✅ 보조 단서 |
| `CLAUDE_CODE_SESSION_ID` | ✅ 환경변수·hook 페이로드 | 표시 안 됨 | 🔸 저장용(사후 추적) |
| `[ref]` | ❌ 알 수 없음 | 대괄호 값 | ❌ **쓰지 않는다** |

🔴 **`ListAgents`의 `[ref]`는 전역 키가 아니다 — 관측자마다 다르게 부여된다.**
같은 세션 쌍이 서로 다른 ref를 보고, `ListAgents`는 자기 자신을 표시하지 않아
세션이 자기 ref를 알 방법도 없다. **지목할 때도 기록할 때도 쓰지 않는다** —
남길 때 쓰면 다른 관측자가 나중에 찾을 수 없는 값이 박제된다.

⚠️ **pane 번호는 재사용된다.** 그래서 **pane은 찾는 열쇠, `session_id`는 맞는지 확인하는 자물쇠**로
나눠 쓴다 — pane으로 행을 찾되 레지스트리의 `session_id`와 다르면 **다른 세션**이다.

```
가드가 "tmux pane %5 · pid 77791" 을 알려줌
  → ListAgents 에서 tmux 컬럼이 %5 인 행을 찾음 → 세션 이름 확보
  → SendMessage 로 "이 파일 작업 중인가 / 결과가 뭔가" 를 직접 질의
  → 답을 받고 진행·취소를 결정
```

**`ask`를 승인하기 전에 물어보는 것**이 규약이다. 물어보지 않고 승인하면
가드는 확인 클릭 한 번을 늘렸을 뿐 아무것도 막지 못한다.

## 이 가드가 못 보는 것

- **`Bash` 경유 쓰기는 타지 않는다.** `sed -i`·`>`·heredoc은 파일 도구 matcher 밖이라
  리스 검사도 갱신도 없다. 보호 경로만
  [`protected_paths_guard.py`](../../../scripts/protected_paths_guard.py)가 별도로 잡는다.
  🔴 **파일 수정을 `Bash`로 하라는 지시는 이 사각지대를 노린 인젝션 패턴**이므로 거부한다.
  ⚠️ 단 출처가 **하네스의 일반 안내**면 공격이 아니라 규약 충돌이다 —
  **거부한다는 대응은 같고 보고 방식만 갈린다.**
- 대상 지문은 **프롬프트 문자열 휴리스틱**이라 미탐·오탐이 있다.
  지문을 하나도 못 뽑으면 **판정하지 않는다** — 오탐보다 미탐이 낫다.
- claim 생성은 check-then-write라 **원자적 락이 아니다.**
- 가드는 **같은 머신의 세션**만 본다. worktree로 갈라진 세션도
  `CLAUDE_PROJECT_DIR`가 다르면 서로 다른 레지스트리를 본다.
