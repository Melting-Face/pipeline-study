# 병렬 세션 — git worktree와 공유 트리 규율

> **범위**: 여러 세션/에이전트가 **하나의 저장소를 동시에** 쓸 때의 규칙이다.
> 브랜치 전략·커밋 단위·커밋 대상 등 **1인 작업 흐름의 정본은 [`../git.md`](../git.md)** 이며,
> 여기서는 중복 없이 링크한다. 요약은 [`CLAUDE.md`](../../../CLAUDE.md) §병렬 세션에 있다.

이 문서가 다루는 것은 두 축이다.

| 축 | 내용 | 언제 읽나 |
| --- | --- | --- |
| **격리** | `git worktree`로 트리를 나누는 방법과 그 **부작용**(피어 감지·`.venv`·`.gitignore`) | 세션 시작 전 |
| **공유** | 트리를 나누지 못한 상태의 규율(pathspec·인덱스 겹침 4축·귀속·판정) | 이미 공유 중일 때 |

**둘은 대체 관계가 아니다** — 격리는 *다음 세션부터* 듣고, 이미 시작한 세션에는 공유 규율만 남는다.


여러 세션/에이전트가 동시에 작업하면 **하나의 워킹트리·인덱스를 공유**해 충돌·오염이 발생한다.
**git worktree**로 브랜치마다 **독립 디렉터리**를 두어 물리적으로 격리한다(같은 저장소·공유 `.git`, 워킹트리만 분리).

- **원칙**: **세션/작업 = 브랜치 = worktree** 1:1:1. 각 세션은 자기 worktree에서만 작업한다.
- 한 브랜치는 **한 worktree에만** 체크아웃 가능하다 → 중복 작업이 자연스럽게 차단된다(암묵적 lock).
- 기본 명령:

  ```bash
  git worktree add ../<repo>-<branch> -b <type>/<요약>   # 새 브랜치+디렉터리 생성
  git worktree list                                      # 현황 확인
  git worktree remove <path>                             # 작업 종료 후 제거
  git worktree prune                                     # 잔여 메타 정리
  ```

- **이점**: 세션 간 working tree 충돌 0, `stash`/브랜치 스위치 불필요, 빌드·캐시 분리.
- **주의**: 디스크 사용↑. `.env`·`.venv` 등 **비커밋 파일은 worktree마다 별도 준비**한다(공유되지 않음).
  → 이 준비를 자동화한 것이 **`scripts/worktree-new.sh`** 다(아래 "도입 절차"). 맨손으로 `worktree add`만
  하면 **피어 감지가 조용히 꺼진다** — 반드시 스크립트를 쓰거나 아래 링크 목록을 직접 잇는다.
- **AI 보조**: 병렬 에이전트는 각자 worktree에서 격리 작업한다([`git.md`](../git.md) §6과 함께 적용).
  Claude Code 서브에이전트는 `isolation: worktree`로 임시 worktree를 자동 사용할 수 있다.

## 왜 지켜지지 않는가 (실측)

규칙이 있어도 **세션은 그냥 저장소 루트에서 시작**한다. 이 날 4개 세션이 전부 main 워킹트리에서
돌았고, 다음 증상이 나왔다.

| 증상 | 실제로 일어난 일 |
| --- | --- |
| **커밋 분리 불가** | `docs/conventions/agents.md` 한 파일에 4개 미션의 변경이 218줄 섞임 → [`git.md`](../git.md) §2("한 커밋 = 한 관심사")를 지킬 수 없음. `-i`/`-p` 미사용 규약이라 헝크 분리 경로도 없음 |
| **인덱스 경합** | 한 세션이 `git add` 해둔 것을 다른 세션이 `git status`에서 자기 것으로 오인 |
| **같은 파일 동시 생성** | `.claude/settings.json`을 두 세션이 각자 만듦(권한 게이트 / hook 배선). 겹치지 않아 무사했으나 **우연**이다 |
| **브랜치 전환 불가** | 다른 세션이 같은 트리를 쓰는 중이라 `git switch`가 그들의 발밑을 흔든다 → main 직접 커밋 외 선택지가 없어짐([`git.md`](../git.md) §1 위반) |

**규칙**:

- **세션 시작 시 `git worktree list`로 자기 위치를 확인**한다. main 워킹트리에 다른 세션이 있으면
  자기 worktree를 만들고 옮긴다 — 작업을 시작한 **뒤에는 늦다**(옮기려면 워킹트리를 건드려야 하고,
  그 순간 다른 세션의 변경이 위험해진다).
- **이미 섞여버렸다면 브랜치를 옮기지 말고**, 관심사별로 나눠 커밋한 뒤 정리한다. 되돌리기 전에
  `git stash create` + `git update-ref refs/backup/<이름>`으로 **워킹트리를 건드리지 않는 스냅샷**을
  떠둔다(`stash push`와 달리 작업 내용이 되돌아가지 않는다).
- 🔴 **공유 트리에서는 `git commit -- <경로…>`로 pathspec을 못 박는다**(사고 후 신설).
  인덱스는 세션 간 **공유 자원**이라, 내가 `git add` 한 것만 인덱스에 있다는 보장이 없다.
  pathspec을 주면 커밋 대상이 **명령 안에서 확정**되고 다른 세션의 스테이징분이 딸려갈 수 없다.
  ```bash
  git commit -- docs/skills.md .claude/agents/skill-matcher.md   # ✅ 대상이 명령에 박힌다
  git add <내 파일> && git commit                                  # ❌ 인덱스의 남의 것까지 간다
  ```
- 공유 트리에서 불가피하게 커밋할 때는 **스테이징 후 `git diff --cached --stat`으로 내 파일만
  올라갔는지 반드시 확인**한다. pre-commit이 미스테이징 변경을 임시 stash·복원하므로, 그 과정이
  정상이었는지도 커밋 직후 `git status`로 본다.
  **다만 확인만으로는 부족하다** — 확인과 커밋 사이에 **다른 세션이 스테이징할 창(window)** 이 남는다.
  실제로 `git status` 확인 후 커밋했는데 그 사이 스테이징된 남의 파일 2개가 실려 나갔다(`a95af44`).
  **확인은 창을 좁히고 pathspec은 창을 없앤다** — 둘 다 한다.

## 도입 절차 — `scripts/worktree-new.sh`

`git worktree add`는 한 줄이다. 실제 마찰은 **gitignore된 자산이 새 worktree에 없다**는 것이고,
그 준비를 사람이 매번 기억해야 하면 규칙은 조용히 샌다. 그래서 배선을 스크립트에 박았다.

```bash
./scripts/worktree-new.sh <type>/<kebab-요약> [--venv]
# 예: ./scripts/worktree-new.sh feat/spark-thrift-poc --venv
```

하는 일: 브랜치명 규약([`git.md`](../git.md) §1) 검사 → **브랜치 상태 4축 판정** → `worktree add` →
**비커밋 자산 심볼릭 링크** → (옵션) `uv sync` + `dbt deps`.

**새 브랜치만 만드는 게 아니다.** 브랜치 상태를 넷으로 갈라 처리한다 — 신규는 `-b`로, 로컬에 이미
있으면 `-b` **없이** 붙이고, 원격에만 있으면 `origin/<B>`를 **시작점으로 명시**해 추적 브랜치를
만들며, 다른 worktree가 점유 중이면 **어느 디렉터리가 쓰고 있는지 알려주고 멈춘다**.

⚠️ 마지막 축은 실패가 아니라 **설계**다. 한 브랜치는 한 worktree에만 체크아웃되고 그게 중복 작업의
암묵적 lock이므로([`git.md`](../git.md) §7), 스크립트가 우회할 일이 아니라 사람이 고를 일이다.
그래서 분기하지 않고 선택지를 띄운다. 배경·경위는
[`../../architectures/terraform.md`](../../architectures/terraform.md) §운영 메모.

### 발견 ① — worktree는 피어 감지를 **조용히 끈다** (링크로 해결)

세션 충돌 감지(`session_sync_guard.py`)의 레지스트리는 `$CLAUDE_PROJECT_DIR/.claude/.claims`다.
worktree마다 `CLAUDE_PROJECT_DIR`가 다르므로 **레지스트리도 worktree마다 따로 생기고,
모든 세션이 서로를 "나 혼자"로 본다.** 에러는 나지 않는다 — 그냥 경고가 안 뜬다.

이게 위험한 이유는 **worktree가 격리하는 것과 가드가 지키는 것이 다르기 때문**이다.
worktree는 **파일·인덱스**를 격리하지만 **클러스터·컨테이너·DB는 격리하지 못한다**.
가드에 최근 추가된 `SHARED_INFRA_RE`(kubectl·helm·compose)가 정확히 그 영역을 본다.
즉 **파일 충돌을 없애려고 도입한 격리가, 파일로는 못 막는 충돌의 감지를 끄는** 형국이다.

→ 해법은 가드 수정이 아니라 **레지스트리를 링크로 공유**하는 것이다.
`Path.resolve()`가 링크를 따라가므로 가드의 `/.claude/.claims/` 매칭도 그대로 성립한다.

**실측(3셀 대조)** — 동일 페이로드(`git stash list`)로 `CLAUDE_PROJECT_DIR`만 바꿔 실행:

| 셀 | `CLAUDE_PROJECT_DIR` | 결과 |
| --- | --- | --- |
| A 처리군 | 메인 트리 | 피어 **4개** 감지 |
| B 처리군 | worktree(`.claims` 링크) | 피어 **4개** 감지 — A와 동일 |
| C **대조군** | 빈 디렉터리(`.claims` 없음) | **출력 0** |

> C가 이 검증의 핵심이다. A·B만 봤다면 "링크가 먹었다"와 "가드가 원래 항상 경고한다"를
> 갈라내지 못한다. **관측 경로가 살아 있는 것과, 그 관측이 경쟁 가설을 분리하는 것은 다르다.**
>
> **단 "4개"라는 절대 수치는 신뢰하지 마라 — 실세션은 3개였다.** 나머지 둘은 **합성 페이로드
> 테스트가 만든 가짜 엔트리**다(아래 참고). 이 검증이 주장하는 것은 A=B와 C=0이라는 **비교**이지
> 개수가 아니다. 수치를 그대로 인용하면 없는 세션을 있다고 적게 된다.

### 주의 — 이 가드는 **합성 페이로드로 테스트하면 실제 상태를 바꾼다**

`session_sync_guard.py`의 `main()`은 **어떤 서브커맨드든 먼저 `touch_session()`을 부른다.**
따라서 `session_id`를 지어내 stdin으로 넣으면 그 가짜 세션이 **레지스트리에 실제로 등록**되고,
이후 관측에서 살아 있는 피어로 잡힌다(두 세션이 각각 하나씩 오염시킨 사례가 있고,
그 결과가 위 표의 "4개"다). **읽기 전용 검사가 아니다.**
테스트 후에는 `.claude/.claims/sessions/<접두>.json`을 지운다(TTL 90분이라 두면 빠지긴 한다).

### 대가 — 레지스트리 공유는 **git 축에 오탐**을 만든다

`live_sessions()`는 `session_ref`로만 거르고 **`cwd`로 거르지 않는다.** 그래서 링크로 레지스트리를
공유하면 축마다 결과가 갈린다.

| 축 | 링크 공유 후 | 판정 |
| --- | --- | --- |
| 공유 인프라(kubectl·helm·compose) | 다른 worktree 세션도 카운트 | ✅ **정확** — 클러스터는 worktree로 격리되지 않는다(이 링크의 존재 이유) |
| 서브에이전트 중복 | 다른 worktree도 카운트 | ✅ 정확 — 같은 일을 두 번 하는 것은 트리와 무관 |
| 동일 파일 동시편집 | `resolve()`가 worktree별 실경로라 교차 감지 안 됨 | ✅ 정확 — 파일은 실제로 격리됐다 |
| **워킹트리 전역 git**(`switch`·`stash`·`reset`) | 다른 worktree 세션까지 카운트 | ❌ **오탐** |

마지막이 문제다. 경고 문구가 문자 그대로 *"이 워킹트리를 쓰는 다른 세션이 N개"* 인데,
worktree A의 `git switch`는 worktree B의 HEAD를 움직이지 않는다 — **worktree 도입으로 해소된
바로 그 위험에 대해 계속 확인을 올린다.** 그리고 이건 소음 이상이다: **안 뜰 때 안심하는 것이
위험한 만큼, 항상 뜨면 무시하는 법을 배운다.** 같은 채널로 나오는 인프라 축 진짜 경고의
신호 대 잡음비가 깎인다.

✅ **해소됨 (커밋 `adfba1b`)** — `live_sessions(me, worktree=None)`로 **축별 필터**를 넣었다.
git 축만 `worktree`를 넘겨 같은 트리로 한정하고, 인프라 축은 인자를 주지 않아 전체를 유지한다.
판정 키는 `cwd`가 아니라 **`git rev-parse --show-toplevel`** 이다 — 세션을 하위 디렉터리에서 열면
`cwd`가 달라져 같은 트리인데도 다르게 보이기 때문이다. 루트와 브랜치는 **한 번의 git 호출**로 받는다
(hook은 모든 도구 호출마다 돈다). `worktree` 키가 없는 옛 claim은 `cwd`로 대조하며, 세션 TTL이
90분이라 곧 사라진다.

6셀 대조로 검증했다 — **수정 전/후를 같은 입력으로 돌려 대비**시켰다:

| 셀 | 입력 | 기대 | 결과 |
| --- | --- | --- | --- |
| A | `git switch` + **같은 트리** 피어 | 경고 | ✅ 경고(트리 경로·브랜치 표시) |
| B | `kubectl delete` + 두 트리 피어 | **2개 다** 카운트 | ✅ 2개 |
| C | `git switch` + 레지스트리 없음 | 침묵 | ✅ 침묵 |
| **D** | `git switch` + **다른 트리 피어만** | **침묵**(오탐 자리) | ✅ 침묵 / **수정 전엔 경고** |
| E | `kubectl delete` + 다른 트리 피어만 | 경고 | ✅ 경고 |
| F | `git status`(무관 명령) | 침묵 | ✅ 침묵 |

D가 이 수정의 전부이고, **수정 전 버전(`git show HEAD:…`)에 같은 입력을 넣어 경고가 나오는 것**까지
확인했다. 그게 없으면 "고쳤다"와 "원래 안 떴다"를 못 가른다.

**이후 git 축의 침묵은 두 뜻이 된다** — *정말 나 혼자*이거나 *트리가 나뉘었거나*.
인프라 축의 침묵만이 "나 혼자"를 뜻한다. 같은 조용함이라도 읽는 법이 다르다.

링크로 공유하는 자산은 셋이다 — `.env`(비밀정보 사본을 늘리지 않는다)·
`.claude/.claims`(위 이유)·`.claude/settings.local.json`(권한이 갈라지면 worktree마다
프롬프트가 달라진다). `.claude/settings.json`·`agents/`·`commands/`는 **커밋 대상**이라 자동으로 따라온다.

### 발견 ② — `.venv`는 링크하면 **반쪽 격리**가 된다

venv에는 editable 설치(`_editable_impl_dagster_project.pth`)가 들어 있어 **메인 트리의 소스**를
가리킨다. 링크하면 dbt SQL·문서는 격리되는데 **파이썬 코드는 메인 트리 것이 도는** 상태가 되고,
이건 "격리했다"고 믿는 쪽이 더 위험하다. 그래서 **링크하지 않고 `uv sync`** 한다(실측 **1.0~1.2GB**,
uv 캐시가 더우면 **약 60초**). 비용이 있으므로 문서·SQL만 만지는 작업이면 `--venv`를 생략한다
(스크립트 기본값이 생략이다).

**`--venv` 실검증**: 생성된 worktree에서 `dagster_project.__file__`이
**worktree 자신의 소스**를 가리키는 것을 확인했고(격리 성립), 그 venv로
`scripts/spark_connect_smoke.py`를 돌려 **전 항목 통과(exit=0)** 했다.

### 부수 발견 ④ — worktree venv는 **Python 마이너 버전이 갈릴 수 있다**

`requires-python = ">=3.10,<3.15"` 라서 `uv sync`가 **그때 가용한 최신**을 잡는다.
실측: 메인 트리 **3.12.12** / 새 worktree **3.13.9**(같은 커밋·같은 lock인데도).
`dbt-spark 1.11.0`·`pyspark 3.5.9`는 동일했고 스모크도 통과했으므로 지금은 무해하지만,
**"같은 코드인데 인터프리터가 다른" 상태**는 재현성 논의에서 조용히 결론을 가른다
(런타임 컨테이너는 `python:3.13-slim`이라 오히려 worktree 쪽이 이미지와 가깝다).
버전을 맞춰야 하는 검증이라면 `uv sync --python 3.12`처럼 **명시**한다.

### 부수 발견 ③ — `.gitignore`의 **끝 슬래시**가 링크를 놓친다

`.claude/.claims/`처럼 **슬래시로 끝나는 패턴은 디렉터리만** 매칭한다. worktree에서 이 경로는
메인 트리를 가리키는 **심볼릭 링크(=파일 취급)** 라 무시되지 않고 `??`로 잡히고,
그 결과 `git worktree remove`가 *"contains modified or untracked files"* 로 **거부**한다.
→ 루트 `.gitignore`를 **슬래시 없는 `.claude/.claims`** 로 바꿨다(디렉터리·링크 양쪽을 덮는다).
`.env`·`settings.local.json`은 원래 슬래시가 없어 문제가 없었다 — **`.claims`만** 걸렸다.

> 검증도 대조로 했다: 수정된 패턴을 `core.excludesFile`로 주입하면 링크가 무시되고(`check-ignore` 적중),
> 기존 패턴만으로는 무시되지 않아 **원래 증상이 그대로 재현**된다.

정리 시 `--force`가 필요하면 붙여도 된다 — **`--force`는 링크 자체만 끊고 원본을 지우지 않는다**
(제거 후 `.env` 44줄·`claims` 세션 5개·`settings.local.json` 전부 무사함을 실측했다).

### 한계 — 이미 시작한 세션은 옮길 수 없다

`CLAUDE_PROJECT_DIR`는 세션 시작 시 고정되므로 **실행 중인 세션은 자기 worktree로 이주하지 못한다.**
따라서 이 도입은 **다음 세션부터** 효력이 있고, 지금 main 트리를 공유 중인 세션들에는
**pathspec 의무(위)가 계속 유일한 방어선**이다. 둘은 대체 관계가 아니라 **시간축이 다른 방어**다.

## 교차 오염의 3변종 — 정정 가능성은 단계적으로 줄어든다

pathspec을 **양쪽 다 지켰는데도** 하루에 세 번 섞였다. **pathspec은 파일을 가르지 hunk를 가르지
못하기** 때문이다 — 세 세션이 `CLAUDE.md`·`docs/conventions/agents.md`를 함께 들고 있으면
같은 파일 안의 남의 변경은 원리적으로 분리되지 않는다.

| 차수 | 상황 | 무슨 일이 났나 | 닫히는가 |
| --- | --- | --- | --- |
| 1차 | 상대가 **살아 있고 통보 가능** | 커밋 본문에 귀속 명시 | ✅ 사전에 닫힌다 |
| 2차 | 살아 있는 상대가 **둘인데 하나만 관측** | **귀속 오기재** — 대화 중이던 피어가 하나뿐이라 diff의 남의 hunk를 전부 그쪽으로 넘겨짚었다 | ⚠️ 사후 기록으로만 |
| 3차 | 상대 세션이 **종료** | 확인 자체가 불가 | ❌ 안 닫힌다 |

- **2차의 교훈**: 귀속을 적기 전에 **`ListAgents`로 살아 있는 세션을 전부 세라.** "지금 대화 중인
  상대"는 "그 파일을 만진 상대"와 다르다. 관측 범위 편향이 그대로 커밋 본문에 박힌다.
- **1·2차는 통보로 닫히므로 규약이 막아야 하는 것은 3차**다. 아래 두 조항이 그것이다.

## 겹침은 네 축이다 — pathspec으로 풀리는 것은 하나뿐

세션 넷이 한 트리를 공유한 날 실측했다. **"파일이 겹치는가"는 네 축 중 하나만 답한다.**

| 축 | 증상 | 해소 수단 |
| --- | --- | --- |
| ① **파일 겹침** | 남의 파일이 내 커밋에 딸려온다 | `git commit -- <경로…>` pathspec |
| ② **hunk 겹침** | 같은 파일 안에 둘의 변경이 섞인다 | `git apply --cached`로 인덱스 경유 — **pathspec 무효** |
| ③ **전역 상태 겹침** | 파일이 안 겹치는데 **아무도 커밋을 못 한다** | 없음 — **직렬화된다.** 소유자가 커밋해야 풀린다 |
| ④ **인덱스 겹침** | 파일도 hunk도 안 겹치는데 **통합(merge·rebase)이 거부된다** | 상대가 인덱스를 비워야 한다 |

**③ 실측** — `.pre-commit-config.yaml`이 미스테이징이면 pre-commit이 **전역으로 기동을 거부**한다.

```
[ERROR] Your pre-commit configuration is unstaged.
`git add .pre-commit-config.yaml` to fix this.
```
*(관측 주체 `23f895` — 자기 파일만 pathspec으로 담았는데도 막혔다)*
그날 **세 세션의 커밋이 이 파일 하나에 직렬화**됐다. 남의 파일을 `git add`로 스테이징하는 것은
①을 유발하므로 답이 아니고, 해법은 **소유자가 커밋하는 것**뿐이다.

**④ 실측** — 남의 staged 엔트리 때문에 merge가 거부됐다.
```
error: Your local changes to the following files would be overwritten by merge:
  .claude/agents/security.md CLAUDE.md docs/README.md …
```
원격 차이는 무관한 파일 하나뿐이었고 커밋 대상도 안 겹쳤는데 **통합 자체가 막혔다.**

**§인덱스 경합(위 표)이 적은 증상은 *"자기 것으로 오인"* 이고 이것은 *"통합이 거부됨"* 이다.**
같은 이름 아래 다른 증상이라 그 항목만 읽고는 이 상황을 예측할 수 없다.

### 판정 수단 — `git status` 한 자리로 읽지 않는다

`git status --porcelain`의 코드는 **두 자리**이고 앞자리가 인덱스 축이다.

- ` M` = unstaged만 · `M ` = staged · `MM` = staged + 이후 추가 수정
- `grep '^ '` 같은 필터는 **staged를 통째로 지나친다**

⇒ **`merge`·`rebase`·`pull` 직전에는 `git status`가 아니라 `git diff --cached --name-only`를 본다.**

이 사고의 기제는 **관측 부재가 아니라 판독 실패**다. 당사자 자기 진단(`23f895`):
> *"나는 `git status --porcelain`을 **읽고도** 앞자리를 안 봤다. **관측을 했는데 못 본 것**이라
> '안 봤다'보다 나쁘다."*

원칙 7("부정 결과는 관측 경로 생존을 함께 확인")과 **축이 다르다** — 경로도 출력도 살아 있었고
읽는 쪽이 필드를 흘렸다. 가까운 것은 [`philosophy.md`](../../philosophy.md) §계측 단위다.

### `git add <파일>`은 **집행 시점**을 담는다 (②의 확장판)

같은 날 한 세션이 커밋 직전 `--stat`에서 남의 변경 3파일이 딸려온 것을 발견해 되돌렸다.

- 18:50:47 관측 시 `CLAUDE.md`는 12줄 변경이었는데, 18:53 집행 시 **23줄**이었다
- 원인: hunk 분리(`git apply --cached`)를 **일부 파일에만** 쓰고 나머지는 whole-file `git add`로 담았다

⇒ 세 가지가 따라온다.
1. **부분 적용은 안전하지 않다** — 패치를 뜬 파일 집합과 커밋하는 파일 집합이 **같아야** 한다.
2. **패치를 다시 뜨는 것으로는 못 이긴다** — 뜨는 순간과 적용하는 순간 사이가 비어 있고, 상대가
   살아 있는 한 그 창은 계속 열린다. **경주를 빨리 하려 하지 말고 창을 닫아라** — 상대에게
   **쓰기 정지를 요청**하는 것이 그날 유일하게 통한 수단이었다(요청 6분, 그 사이 상대 쓰기 0건).
3. **정지는 상대의 협조로만 성립한다.** `session_sync_guard.py`는 *중복 작업*을 잡지 *동시 인덱스
   접근*을 잡지 않는다. 기계가 아니라 규율이므로 **"가드가 막아주겠지"로 읽지 마라.**

**마지막 그물은 커밋 직전 `git diff --cached --stat` 재확인**이다. 그날 사고를 거기서 잡았다.

## `git add`와 pathspec을 **섞으면** 조용히 반만 커밋된다 (실측)

위 §pathspec 규칙은 *"`git add` 대신 `git commit -- <경로>`"* 인데, **둘을 섞었을 때**
무슨 일이 나는지는 적혀 있지 않았다. 실측 결과 **유실이 아니라 누락이 나고, 에러가 나지 않는다.**

한 파일만 `git add`한 상태에서 **세 파일**을 pathspec으로 커밋했더니 **`git add`한 하나만** 들어갔다.

- **원인은 pre-commit이다.** 훅이 **unstaged 변경을 임시 스태시**하므로, 스테이징 안 된 나머지 둘이
  훅 실행 중 원상복구돼 **"변경 없음"으로 관측**됐다.
- **경고가 없다.** 출력의 `1 file changed`를 세지 않으면 모른 채 지나간다.
  작업 트리에는 변경이 그대로 남아 있어 `git status`로도 이상해 보이지 않는다.

⇒ **인덱스를 비운 채 `git commit -- <경로…>` 하나만 쓴다.** 섞지 않는다.
⇒ **커밋 직후 `git show --stat`으로 파일 수를 세어** 의도한 수와 맞는지 본다.
   위 §확인 규칙이 `git diff --cached`를 쓰라고 하는데, **공유 인덱스에서는 그것이 남의 스테이징도
   보여준다.** 내 커밋에 무엇이 들어갔는지는 **커밋 후에만** 정확히 관측된다.

**`index.lock` 충돌은 기다린다. 절대 지우지 않는다** — 피어의 커밋이 진행 중이라는 신호이고,
지우면 그쪽 커밋이 깨진다. `git reset`으로 피어 스테이징을 내리는 것도 같은 이유로 금지다
(커밋 직전이면 발밑을 흔든다).

## 종료된 세션의 미커밋 작업을 커밋할 때

워킹트리에 **작성 세션이 종료된 미커밋 변경**이 남아 있고, 내 작업과 같은 파일에 얽혀 분리할 수
없으면 다음을 지킨다.

1. **살아 있는 세션 전부에게 소유권을 확인한다**(`ListAgents` → `SendMessage`). 전원이 부인해야
   "종료된 세션의 것"으로 판정한다 — 한 곳만 물으면 2차 유형이 된다.
2. **커밋 본문에 귀속 불명을 명시한다.** 어느 파일의 어느 부분이 이 세션의 작업이 아닌지 적는다.
3. **귀속만 적고 끝내지 않는다** — 아래 조항이 이어진다.

## 미확인 코드를 커밋할 때는 **리뷰 주체를 명시**한다

> **귀속(누가 썼나)과 검증(그 코드가 맞나)은 다른 축이다.** 귀속은 사후 기록으로 정정할 수 있지만
> **검증은 기록으로 닫히지 않는다.** 작성 세션이 종료돼 확인이 불가능한 미커밋 코드를 커밋할 때는,
> 귀속 불명을 적는 것으로 끝내지 말고 **그 코드를 읽고 커밋한 세션이 리뷰 주체임을 본문에 명시**한다.
> 커밋은 "이게 누구 것인지 모른다"가 아니라 **"내가 읽었고 책임진다"** 를 뜻해야 한다.

본문에 **확인한 것과 확인하지 못한 것을 갈라** 적는다. "리뷰했다"만 적으면 무엇이 검증되지 않은
채로 들어갔는지 다음 사람이 알 수 없다.

적용례 `4dc6e1c` — `scripts/worker_path_guard.py` 151줄과 `session_sync_guard.py`의 증분 대부분이
종료 세션의 작업이었다. 본문에 리뷰 주체를 적고, **읽고 확인한 것**(정규식 분기·경로 판정 로직·
구문·ruff)과 **확인하지 못한 것**(`PreToolUse` matcher 실발동, `NotebookEdit` 실재 여부)을 갈라 남겼다.
그 "확인하지 못한 것"이 곧바로 다음 검증 항목이 됐고, **실제로 배선 누락이 발견됐다**(§아래).

## 커밋했다고 실행되는 것은 아니다 — 배선 확인

`4dc6e1c`가 추가한 `scripts/worker_path_guard.py`는 **어떤 에이전트 정의에도 배선돼 있지 않다.**
`.claude/agents/` 전체에서 이 스크립트를 참조하는 곳은 **0곳**이고, 유일한 워커 훅은
`analyst.md` → `analyst_path_guard.py`(구 단일 워커 버전)다.

즉 **호출자 없는 가드**가 커밋됐다. 파일 자체는 문법·로직이 멀쩡하고 테스트도 통과하므로
**아무 신호도 나지 않는다** — `escalate` 무효 enum과 정확히 같은 계열(§`docs/conventions/agents.md`
§hook 결정값)이다. 차이는 그때는 *잘못된 값*이었고 이번엔 *아무도 부르지 않는 코드*라는 것뿐이다.

- **가드·훅을 추가하면 배선까지가 한 벌이다.** `scripts/`에 파일을 놓는 것은 절반이고,
  `.claude/settings.json`(세션 전역) 또는 워커 프론트매터(워커 한정)에 거는 것이 나머지다.
- **확인법**: `grep -rn '<스크립트명>' .claude/` 가 0건이면 그 가드는 **죽어 있다.**
- 배선한 뒤에는 **일부러 위반시켜** 가드의 `permissionDecisionReason` 원문이 나오는지 본다
  (auto 모드 분류기가 막은 것과 **문구 출처로 갈린다**).

## 공유 트리에서 파일이 사라졌을 때

공유 트리에서 **파일이 안 보인다**는 관측은 삭제·유실이 아닌 경우가 대부분이다.
3자 병렬 세션에서 실제로 오경보 1건과 **결론은 맞는데 메커니즘을 지어낸** 정정 1건이 났다.

| 주체 | 관측 | 판단 | 결과 |
| --- | --- | --- | --- |
| 세션 A | (당사자) | 공유 트리에 `.github/workflows/ci.yml`을 untracked로 만들었다가, worktree로 격리 이동한 뒤 **공유 트리 사본을 `rm`** — 피어에게 untracked 노이즈를 안 남기려는 의도 | 정상 행위 |
| 세션 B | 시작 스냅샷 ↔ 현재 상태 비교에서 파일이 없음 | **"소실·복원 불가"** → 경보 상신 | ❌ **오경보** |
| 세션 C | `git log --all --diff-filter=D` **0건** | "소실이 아니다"(✅ 맞음) + **메커니즘을 `git switch`로 서술**(❌ 추측) | ⚠️ 절반만 맞음 |

**규칙 3축 + 1**

1. **tracked 여부를 작업 트리로 판정하지 않는다.** 작업 트리의 추적 상태는 **저장소 전체의
   추적 상태가 아니다** — 전형적인 **모집단 문제**([philosophy.md](../../philosophy.md) §계측 단위 ④).
2. **삭제 판정은 히스토리로 한다** — `git log --all --diff-filter=D -- <path>`. **0건이면 삭제가 아니다.**
   이어서 `git for-each-ref --contains <commit>`으로 **어느 브랜치에 사는지**까지 본다.
3. **공유 트리에서는 다른 세션의 *정상 행위*가 삭제와 같은 증상을 만든다** — worktree 이동·`rm`·
   `checkout`·`switch`가 전부 "내 시작 스냅샷에 있던 파일이 지금 없다"로 관측된다.
   ⇒ **증상은 원인을 지목하지 않는다.**
4. **결론이 맞아도 메커니즘을 추측해 적지 마라.** 관측·결론·메커니즘은 **다른 축**인데
   한 문장에 눌리면 다음 사람이 **추측을 사실로 읽는다.** 당사자 자기보고 전까지 메커니즘은
   **`미확인`** 이다(위 표에서 실제 원인은 의도적 `rm`이었고 `git switch`가 아니었다 —
   당사자 자기보고로 확인).

**판정 실행례**(공유 트리 로컬 `main`=`a7cdf59` 기준 · 관측 시각은 `date`로 실측)

```bash
git log --all --diff-filter=D --oneline -- .github/workflows/ci.yml   # → 0건 (삭제 아님)
git log --all --oneline        -- .github/workflows/ci.yml            # → 1건 (6e1e2b8)
git for-each-ref --contains 6e1e2b8                                    # → origin, origin/main
git merge-base --is-ancestor 6e1e2b8 main                              # → 비-0 (로컬 main엔 없음)
git rev-list --left-right --count main...origin/main                   # → 0  1 (1 behind)
```

- ⇒ **파일은 삭제된 적이 없고 `origin/main`에 tracked로 존재**한다. 로컬 작업 트리에 안 보인 것은
  로컬 `main`이 **1커밋 뒤처져** 있었기 때문이다.
- **`--all`은 원격 추적 레퍼런스를 포함하므로, 로컬만 보는 판정과 모집단이 다르다.**
  "없다"를 주장하기 전에 **무엇을 세어 0건인지**(로컬 트리 / 로컬 브랜치 / `--all`)를 함께 적는다.
- **경보를 올릴 때도 관측 시각과 기준선(`HEAD` ↔ 워킹트리 ↔ `origin/*`)을 함께 적는다** —
  세션 B의 오경보는 값이 틀린 게 아니라 **기준선을 안 밝힌** 것이 원인이다
  ([philosophy.md](../../philosophy.md) §⑦ 기준선이 갈린 정답).
