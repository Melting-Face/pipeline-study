# GitHub Issue 규약

이 문서가 정하는 것은 **Issue에 무엇을 붙이고 어떻게 쓰는가**다.
**무엇을 Issue로 낼지**(행선지 판정)는 [`doc-sync.md`](../doc-sync.md) §실무 규칙 7 축 3(위협)이 정본이며,
여기서 되풀이하지 않는다.

> **이 문서가 담지 않는 것** — 열린 Issue의 현황·우선순위 배분 실태는 저장소 밖
> `$OBSIDIAN_VAULT/status/backlog.md`에 있다. 여기에는 **규칙만** 둔다.

---

## 1. 등록 전 — 공개 판정이 먼저다

🔴 이 저장소는 공개라 **Issue도 공개다.** 등록 전에 [`doc-sync.md`](../doc-sync.md) §실무 규칙 7
**축 3(위협)** 으로 판정한다.

| | 행선지 |
| --- | --- |
| 규칙·처방·기능 결함·문서 갭·이행 대기 | **GitHub Issue** |
| 인프라 공격 표면·시크릿 스캔 결함·관측 공백 지도·CVE 표면 | **볼트** `status/`·`security/` |

**갈리면 볼트가 기본값**이다 — 공개는 되돌릴 수 없다.

---

## 2. 라벨 — 2축, 둘 다 필수

**`area:*` 1개와 `prio:*` 1개를 붙인다.** 하나만 붙은 Issue는 미완성으로 본다.
두 축은 독립이며 서로를 대체하지 않는다.

### 축 1 — 분류 `area:*` (파일 경로 기준)

| 라벨 | 범위 |
| --- | --- |
| `area:docs` | `docs/**` · `README.md` · 규약 문서 |
| `area:infra` | `k8s/**` · `terraform/**` · `compose.yml` · Dockerfile |
| `area:pipeline` | `dagster_project/**` · `models/**` · 적재·변환 |
| `area:agents` | `.claude/**` · `.codex/**` · 워커·스킬·가드 스크립트 |
| `area:ci` | `.github/workflows/**` · pre-commit · 린트 게이트 |

**기준이 "파일 경로"인 이유**: 붙이는 사람이 *판정하지 않고* 경로만 보고 고를 수 있다.
커밋 type 기준(`area:fix` 같은)을 쓰지 않는 것은 **제목이 이미 type을 담고 있어** 같은 정보를
두 번 적게 되기 때문이다 — 라벨은 *"어떤 종류의 변경인가"* 가 아니라 *"무엇에 관한 것인가"* 를 센다.

### 축 2 — 작업 우선순위 `prio:*`

**무엇부터 할지**를 정한다. `area:*`가 *"무엇에 관한 것인가"* 를 센다면 이 축은
*"언제 손대는가"* 를 센다.

| 라벨 | 뜻 | 붙이는 기준 |
| --- | --- | --- |
| `prio:high` | 먼저 한다 | 다른 작업을 **막고 있거나**, 방치하면 **비용이 계속 커진다** |
| `prio:medium` | 다음 사이클에 한다 | 막지는 않으나 **할 것이 정해져 있다** |
| `prio:low` | 일정 없음 | 열어는 두되 **착수 시점을 정하지 않는다** |

판정 기준을 **"얼마나 중요한가"가 아니라 "먼저 해야 하는가"** 로 두는 이유는, 중요도는
판정자마다 갈리고 시간이 지나도 안 변하는 척하기 때문이다. 위 두 기준(**막고 있는가** /
**비용이 커지는가)** 은 바깥을 가리키므로 확인할 수 있다 — 막고 있다면 *막힌 작업을 지목*할 수
있어야 하고, 그 작업이 끝나면 **저절로 강등된다.**

🔴 **갈리면 낮은 쪽을 고른다.** 전부 `high`가 되면 축이 있으나 없으나 같아진다.
`prio:high`가 늘어나는 것은 우선순위가 높아진 것이 아니라 **판정이 무너진 것**이다.

**등급을 늘리지 않는다.** 3단계로 못 가르는 상황이 반복되면 그것은 등급이 모자란 게 아니라
**분모(열린 Issue 수)가 커진 것**이므로, 등급을 쪼개기 전에 닫는 것을 먼저 검토한다.

#### ⚠️ 표시 순서는 우선순위 순이 아니다

라벨 이름에 번호 접두어(`prio:1-high` 같은)를 **두지 않기로 했다.** 그 대가로
**정렬이 우선순위를 보장하지 않는다** — 이름만 보고 `high > medium > low` 순으로 표시되리라
가정하지 않는다.

관측된 것: `gh label list`의 **API 응답 순서는 `high` → `medium` → `low`** 였다
(알파벳순이 아니다 — 알파벳순이면 `high` → `low` → `medium`이 된다).
**미확인**: GitHub **웹 UI**의 라벨 목록·Issue 배지 표시 순서. API 순서를 UI 순서로 읽지 않는다.

⇒ 순서가 중요한 조회는 표시에 기대지 말고 **명시적으로 거른다**:

```
gh issue list --label "prio:high"
```

### 값을 늘릴 때

빈 라벨은 분류를 흐린다. **실제로 붙일 Issue가 생겼을 때** 추가하고, 그전에 미리 만들지 않는다.
`area:*`는 저장소 최상위 디렉터리 구조를 따르므로, 새 최상위 축이 생기면 그때 함께 는다.

## 3. 제목·본문

- **제목**은 커밋과 같은 `type(scope): 설명` 형태를 쓴다(한국어 설명).
  ⚠️ 이것은 **관행이자 템플릿 프리필**이지 게이트가 아니다 — gitlint는 `commit-msg` 스테이지에서만
  돌아 Issue 제목을 보지 않는다. 커밋 규약 정본은 [`general.md`](general.md) §커밋 메시지다.
- **본문**은 `.github/ISSUE_TEMPLATE/`의 폼을 따른다. 폼이 강제하는 칸 중 하나는
  **「하지 않은 것」** 이다 — 이 칸이 없으면 *"확인했다"* 와 *"안 해봤다"* 가 구분되지 않는다
  ([`../philosophy.md`](../philosophy.md) 원칙 7).
- 수치를 적을 때는 **그 값이 무엇을 세는지**(계측 단위)를 함께 적는다.
- **관측 일자·실측 수치는 Issue가 받는다.** `docs/`에서 걷어낸 시제성 있는 값의 행선지가
  여기다([`doc-sync.md`](../doc-sync.md) §실무 규칙 7 축 2).

## 4. 템플릿

`.github/ISSUE_TEMPLATE/`에 셋을 둔다.

| 파일 | 용도 | 고정 라벨 |
| --- | --- | --- |
| `config.yml` | 빈 Issue 차단 + 보안 신고를 Issue 밖으로 유도 | — |
| `task.yml` | 규칙·문서 갭·이행 대기 등 열린 작업 | 없음 |
| `bug.yml` | 선언과 다르게 동작하는 결함 | `bug` |

## 5. 🔴 이 규약은 강제되지 않는다

**"라벨을 필수로 정했다"를 "라벨이 붙는다"로 읽지 않는다.**

| 수단 | 실제로 하는 일 | 강제인가 |
| --- | --- | --- |
| 이 문서 | 기준을 정의한다 | ❌ 규율 |
| 라벨 `description` | 붙이는 사람이 GitHub UI에서 기준을 본다 | ❌ 규율 |
| 템플릿 `dropdown` | **본문에 기록**시킨다 | ❌ **라벨을 붙이지 않는다** |
| 템플릿 `labels:` | 템플릿마다 **고정 라벨 1개**만 붙인다 | ✅ 단 선택 불가 |
| `blank_issues_enabled: false` | 폼을 우회한 빈 Issue를 막는다 | ✅ |

⚠️ **`dropdown` 선택은 라벨이 되지 않는다.** 선택값은 Issue 본문에 텍스트로 들어갈 뿐이므로,
**생성 후 사람이 `area:*`·`prio:*`를 직접 붙여야 한다.** 이것을 자동화하려면 Actions 워크플로가
필요하고, 지금은 **두지 않았다**(선언 없이 빠뜨린 것과 구분하기 위해 여기 명시한다).

⚠️ **`labels:`에 존재하지 않는 라벨을 적으면 GitHub은 조용히 무시한다** — Issue는 생성되고
라벨만 안 붙는다. 그래서 **라벨을 먼저 만들고 템플릿을 나중에 고친다.** 순서를 뒤집으면
"설정했는데 안 붙는" 상태가 에러 없이 남는다.

### 아직 검증되지 않은 것

**GitHub 이슈 템플릿은 기본 브랜치에 있어야 작동한다.** 이 템플릿이 `main`에 병합되기 전까지
아래 넷은 **미확인**이며, 병합 직후 실제로 Issue를 1건 열어 확인한 뒤에야 "작동한다"고 쓸 수 있다.

- [ ] 템플릿이 Issue 생성 화면에 선택지로 뜨는가
- [ ] `blank_issues_enabled: false`로 빈 Issue 경로가 실제로 사라지는가
- [ ] `bug.yml`의 고정 라벨 `bug`가 실제로 부착되는가
- [ ] `dropdown` 선택이 라벨로 **부착되지 않는다**는 것 (위 표의 근거 — 반증되면 표를 고친다)

로컬에서 통과한 것은 **YAML 파싱과 폼 스키마 자체점검까지**다. 그것은 *"파서에 맞았다"* 이지
*"GitHub이 렌더링한다"* 가 아니다.
