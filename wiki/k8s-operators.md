# 오퍼레이터를 둘 것인가 — 맡기면 무엇이 내 손을 떠나는가

> 학습 노트. 배치·스트리밍·데이터베이스에는 오퍼레이터를 두고, 오브젝트 스토리지와
> 오케스트레이터에는 두지 않으면서 배운 것.
> 결론부터 쓰면 — **오퍼레이터는 기능이 아니라 「층」이고, 그 층은 선언을 줄이는 대신
> 관측 지점을 한 칸 밖으로 옮긴다.**

## 왜 「쓴다 / 안 쓴다」가 답이 아닌가

처음에는 이분법으로 접근했다. 실제로 세워 보니 **층이 셋**이고 층이 있는 것과 없는 것이 공존한다.

```text
층            선언 형태        소유 주체
오퍼레이터    Helm 차트        선언 스택
CR            raw YAML         상주 CR = 선언 스택 · 데이터 CR = 셸 · 잡 CR = 런타임
워크로드      raw 매니페스트   선언 스택
층이 아예 없는 것 — 오브젝트 스토리지 · 오케스트레이터 · 상주 SQL 엔드포인트
```

CR 종류도 한 갈래가 아니다 — 배치 잡·스트리밍 세션·데이터베이스 클러스터·데이터베이스 추가·정기 백업·
인증서 발급이 전부 다른 kind이고, 그중 하나는 **백업 플러그인이 CRD만 주고 조정은 본체 오퍼레이터가 한다.**
**CRD와 컨트롤러는 한 덩어리가 아니라 두 조각이고 따로 온다** — 컨트롤러 없는 CRD는 etcd 안의 YAML일 뿐이다.

CRD 자체도 한 버전이 아니다. 한 CRD가 두 버전을 **동시에 제공**하면서 실제 저장 버전은 하나라, 제공되는
쪽으로 적용하면 통과는 하는데 변환되며 전용 필드를 못 쓴다. 설치 순서 축은 [빈 클러스터를 세우며](k8s-bootstrap.md)가 갖는다.

## 오퍼레이터가 실제로 하는 일 — 조정 루프

오퍼레이터는 **CRD + 조정 루프**로 동작한다고 알려져 있다. 원하는 상태를 오브젝트로 선언하면 컨트롤러가
실제 상태를 그쪽으로 수렴시킨다. 그래서 CR 한 장에는 성질이 다른 두 종류의 필드가 들어 있다.
아래는 **개념 골격이며 실행 가능한 매니페스트가 아니다.**

```yaml
apiVersion: <오퍼레이터 API 그룹>/<버전>
kind: <커스텀 리소스>
spec:                 # 내가 쓴다
  instances: <개수>
  storage: <용량>
  parameters: <튜닝 값>
status:               # 오퍼레이터가 쓴다 — 내 자리가 아니다
  phase: <관측된 상태>
```

**`status`의 소유자가 내가 아니라는 점** — 뒤에 나오는 가장 비싼 실패가 전부 여기서 파생된다.

```text
선언(spec) ─▶ 관측 ─▶ 차이 계산 ─▶ 조치 ─▶ 상태 기록(status)
    ▲                                              │
    └──────────────── 다시 관측 ◀──────────────────┘
```

이 루프가 흡수하는 범위는 생각보다 넓다. 데이터베이스 오퍼레이터의 경우 볼륨 클레임·failover·시점
복구·서버 파라미터 튜닝이 **CR 한 장의 필드 선언**으로 들어온다 — 직접 짜면 절차서 여러 장이 될 것들이다.

## 무엇을 보고 채택을 정했나 — 세 기준

| 대상 | 판정 | 한 줄 근거 |
| --- | --- | --- |
| 데이터베이스 | **채택 ✅** | 막을 유실 급소가 컸다 |
| 오브젝트 스토리지 | **미채택 🔎** | 상주 자원은 느는데 막을 급소가 없다 |
| 오케스트레이터 | **층 자체가 없음 🔎** | 차트의 전제가 이 프로젝트의 선택과 어긋난다 |

**데이터베이스.** 이전 구성은 평범한 배포 선언에 임시 볼륨이라 **파드 재기동만으로 카탈로그가 소멸했다.**
데이터 파일은 남는데 「어떤 테이블이 어디 있는지」가 사라져 복구가 곧 전량 재적재였다. 이제 그 급소가 CR 한 장 안이다.

**오브젝트 스토리지.** 오퍼레이터를 두면 마스터·볼륨·파일러가 갈리며 **상주 자원이 CPU 반 개와 메모리
1기가 남짓 순증**하는데, 이쪽은 이미 영속 볼륨이라 재기동으로 잃을 것이 없다. **대가는 명확한데 살 것이 없다.**

**오케스트레이터.** 공식 차트를 안 쓴 이유는 품질이 아니라 **전제**다 — 특정 run launcher·별도 코드서버·자체
데이터베이스 하위 차트를 전제로 설계돼, 고른 셋을 **전부 override**해야 한다. 그래서 워크로드 축 하나만 둔다.

⇒ 기준은 셋이다 — ⓐ**막을 유실 급소가 있는가** ⓑ**상주 자원 순증이 얼마인가** ⓒ**전제가 내 선택과 맞는가.**
📌 셋 중 어느 것도 **「그 오퍼레이터가 좋은가」를 묻지 않는다.**

## 에러 없이 깨진 것 ① — 조정 루프는 도는데 관측 채널이 죽는다

배치 잡 CR의 상태 요약 필드가 driver 파드가 종료된 뒤에도 **중간 상태에 영구 고착**했다. 몇 시간이 지나도
전이가 오지 않는다. 오퍼레이터 파드는 **재시작 0**이고 GC 로그도 정상이다 — 죽은 것은 **watch**다.

```text
신호                        값            읽히는 뜻
CR 상태 요약 필드           중간 상태     "실행 중이다"
driver 파드 phase           종료 상태     "이미 끝났다"
오퍼레이터 파드 재시작 수   0             "컨트롤러는 멀쩡하다"
세 줄이 동시에 참이다 — 모순이 아니라 관측 채널만 끊긴 모습이다
```

고착은 잡이 아니라 **오퍼레이터의 상주 시간**에 딸린다. 기동 직후에는 전이가 오고, 오래 떠
있을수록 오지 않으며, 롤아웃을 다시 돌리면 다시 온다.

🔴 **오퍼레이터 파드가 살아 있다는 것은 조정 루프가 돌고 있다는 증거가 아니다.**

타임아웃이 통째로 흐른 뒤 **성공한 잡이 실패로 기록**된다 — 잡은 성공했고 테이블에 행도 들어갔는데
**오케스트레이터만 모르는 상태**다. 그래서 글루가 CR 상태와 driver 파드 phase를 **함께** 보고, 파드가
종료된 뒤 유예 창 안에 전이가 없으면 파드 기준으로 탈출하며 판정 문자열에 **왜 그렇게 판정했는지**를
같이 적는다 — `DriverReady(watch-stalled,pod=Succeeded)` 형태다. 이 문자열은 탈출 분기에서만 만들어져
값이 남아 있다는 것 자체가 양성 증거다. 근본 해결은 업스트림의 몫이다.

컨트롤러가 이벤트가 아니라 **현재 상태를 다시 보고 맞춘다**는 것은 공식 API 규약에 적혀 있다.
그런데 그 문장의 동사가 「보장한다」가 아니라 **「그런 설계를 가능하게 한다」**다 — 규범이 아니라
서술이고, 설계를 실현하는 장치인 **주기적 재동기화는 꺼 둘 수 있다**. 클라이언트 라이브러리가
「주기가 0이면 재동기화를 하지 않는다」고 적는다. **「level 기반이니 놓쳐도 복구된다」는 설계
의도이지 런타임 보증이 아니다.**

출력을 어떻게 읽을 것인가는 [kubectl로 판정하기](kubectl-judgement.md)가 갖는다. 다른 것은 **그 출력을 쓰는 주체가 내가 아님**이다.

## 에러 없이 깨진 것 ② — 오퍼레이터가 채운 것을 「없다」로 읽는다

데이터베이스 CR에는 probe도 RBAC도 보안 컨텍스트도 쓰지 않는다. **오퍼레이터가 채우기
때문이다.** 파드를 열어 보면 내가 선언한 적 없는 것들이 이미 들어가 있다.

```text
CR에 쓴 것            파드에 생긴 것
인스턴스 수           비특권 실행 · 읽기전용 루트 파일시스템
스토리지 용량         capability 전량 드롭 · 기본 seccomp 프로파일
서버 파라미터         기동 · 준비 · 생존 3종 probe
부트스트랩 롤         전용 서비스계정 + 자기 시크릿 한정 Role
선언 네 줄            오른쪽 전부 — 정적 감사는 왼쪽만 본다
```

그래서 **CR에 없다고 위반으로 읽지 않는다** — 선언 파일만 훑는 감사는 이 층에서 「보안 컨텍스트 미설정」
같은 **거짓 갭**을 내고 없는 문제를 고치게 만든다. 반대도 나쁘다: 중복 선언하면 오퍼레이터 값과 충돌하고,
남의 필드에 손대면 소유권까지 넘어간다. 그 축은 [kubectl로 판정하기](kubectl-judgement.md)가 갖는다.

거짓 갭의 교과서는 스트리밍 쪽이다. 오퍼레이터의 감시 범위를 네임스페이스로 좁히면 잡의 RBAC도 함께
좁아져 **DDL과 목록 조회는 되는데 쿼리 실행만 거부**다 — 정상 경로가 여럿 통과하니 권한을 의심조차 않는다.

⚠️ 규율은 **양방향**이다 — **갭으로 읽지도, 덮어쓰지도 않는다.**

## 에러 없이 깨진 것 ③ — 차트가 준 권한과 코드가 부르는 동사가 다르다

배치 오퍼레이터 차트는 워크로드용 ClusterRole을 만들어 주는데, 그 **verb 목록이 템플릿에 하드코딩**돼 있어
값으로 조정할 수 없고 **일괄 삭제 권한이 빠져 있다.** 핵심은 **잡이 끝날 때의 정리를 오퍼레이터가 아니라 잡의
driver가 자기 권한으로 한다**는 점이다. driver가 종료하며 라벨 셀렉터로 일괄 삭제를 호출하는데, 권한이 없으면
**잡은 성공한 채로** 서비스와 볼륨 클레임이 남고 에러 로그만 찍힌다.

```text
... is forbidden: User "system:serviceaccount:<잡-ns>:<워크로드 SA>"
    cannot deletecollection resource "services" in API group ""
    in the namespace "<잡-ns>"
```

⇒ **오퍼레이터 차트의 RBAC이 곧 워크로드 RBAC이 아니다.** 보완은 최소권한으로 한다 — ClusterRole을
새로 만들지 않고 **잡 네임스페이스 한정 Role**에 **빠진 동사 하나만** 더한다.

## 에러를 내고 멈춘 것 — 삭제가 영원히 멈춘다

**finalizer는 컨트롤러가 붙이고 컨트롤러만 뗀다.** 선언 도구가 의존 관계를 모르면 삭제 순서를 보장하지
않으므로, **오퍼레이터가 먼저 삭제되면 finalizer를 처리할 주체가 사라져 CR 삭제가 영원히 멈춘다.**

```text
$ kubectl delete <커스텀 리소스> <이름>
  ... 응답 없이 멈춘다
metadata.deletionTimestamp: "<삭제 요청 시각>"
metadata.finalizers: ["<오퍼레이터 그룹>/<정리 작업 이름>"]
```

삭제 타임스탬프는 찍혔는데 finalizer 목록이 남아 있다 — 앞의 사례들과 달리 **에러를 내고 멈춘다.**

⇒ **삭제도 조정의 일부다.** 처방은 CR이 오퍼레이터에 의존한다고 **명시해** 파괴 순서를 역순으로 강제하는
것이다. finalizer를 붙이는 오퍼레이터가 하나뿐이어도 나머지에 함께 건다 — 어느 오퍼레이터든 붙일 수 있다.

## 그럴듯해서 속은 것 ① — 「선언하면 반영된다」가 모든 필드에 걸리지 않는다

같은 CR 안에 **조정 대상 필드**와 **초기화 1회 필드**가 섞여 있다. 데이터베이스 부트스트랩으로 만든 계정의
비밀번호가 후자다 — 시크릿을 새 값으로 바꾸고 다시 적용해도 **DB 롤의 비밀번호는 옛 값 그대로**다.
오퍼레이터가 시크릿 변경을 롤에 반영하는 것은 **「관리 대상 롤」로 선언한 것뿐**이고 부트스트랩 계정은 없다.

증상이 고약하다 — 시크릿을 읽는 워크로드는 인증에 실패하고 옛 값을 들고 있는 경로는 성공해 **부분 성공이라
「바꿨다」로 읽힌다.** 해법은 롤을 선언 관리로 인수하는 것이고, 이미 뜬 워크로드의 환경변수는 손으로 돌려야
해서 **재기동까지가 한 벌**이다.

## 그럴듯해서 속은 것 ② — 폴링하는 클라이언트는 컨트롤러가 아니다

이 저장소에는 **직접 만든 오퍼레이터가 없다** — 컨트롤러 프레임워크 흔적도 직접 정의한 CRD도 전수 확인에서
0건이다. 있는 것은 **CR 제출·폴링 글루**다: 자산 실행 시점에 1회 제출하고 폴링한다. reconcile 루프가 없다.

```text
컨트롤러                         이 저장소의 글루
watch · list                     create  — CR 한 장 제출
patch · update — status 기록     get     — 폴링
소유자 참조로 하위 리소스 생성   list    — 파드 상태 확인
무한 reconcile 루프              delete  — 회수
```

이 차이가 RBAC 설계로 직결된다. **verb는 코드가 실제로 부르는 것만** 넣는다 — 감시·패치·수정은 호출하지
않으므로 넣지 않고, 폴링을 감시로 바꾸는 날 그때 더한다. 미리 넣어두면 **「왜 있는지 아무도 모르는
권한」**이 된다. 직접 만든 컨트롤러가 없어 **작성법은 범위 밖**이다 — 빠뜨린 것이 아니라 고르지 않았다.

## 확인 방법

```shell
# 1. 층이 있는가 — 비면 CRD가 없다. CRD만 있고 컨트롤러가 없으면 아무 일도 안 일어난다
kubectl api-resources --api-group=<오퍼레이터 API 그룹>; kubectl get deploy -n <오퍼레이터-ns>
# 2. 저장 버전 — served와 storage는 다른 축이다
kubectl get crd <CRD 이름> -o jsonpath='{.spec.versions[*].name} {.status.storedVersions}'
# 3. 채워진 것 — CR 한 장을 적용하고, 생긴 파드 spec에서 내가 안 쓴 필드를 센다
kubectl get pod <파드> -o yaml | grep -c 'securityContext\|Probe'
# 4. 권한 대조 — 차트가 준 verb와 내 코드가 부르는 동사를 나란히 놓는다
kubectl get clusterrole <워크로드 ClusterRole> -o yaml
# 5. 삭제 전 — 비어 있지 않으면 붙인 컨트롤러가 이 CR보다 먼저 사라지면 안 된다
kubectl get <커스텀 리소스> <이름> -o jsonpath='{.metadata.finalizers}'
```

3단계 개수가 **정적 감사가 못 보는 갭의 크기**다. 4단계는 양쪽 다 틀릴 수 있다 — 많아도 틀리고 적어도 틀리다.
그리고 **음성 대조가 가장 중요하다**: 전이가 안 오는 CR을 그대로 둔 채 오퍼레이터를 재기동해 다시 제출했을 때
전이가 오면 **죽은 것은 조정 루프가 아니라 관측 채널**이다. 대조군 없이는 둘이 **같은 화면**으로 보인다.

## 출처

개념 서술은 아래 1차 문서에서 대조했다(확인 시점 2026-09-19). 제품 쪽은 각 저장소의 **기본 브랜치**
기준이라 특정 릴리스와 다를 수 있다. 표에 없는 것은 「없다」가 아니라 **고르지 않았거나 확인하지
못한 것**이다.

| 문서 | 링크 |

| Kubernetes API Conventions — Spec and Status | https://github.com/kubernetes/community/blob/master/contributors/devel/sig-architecture/api-conventions.md |
| Kubernetes — Controllers | https://kubernetes.io/docs/concepts/architecture/controller/ |
| Kubernetes — Operator pattern | https://kubernetes.io/docs/concepts/extend-kubernetes/operator/ |

**확인하지 못한 것도 적는다.** 「부트스트랩 계정의 비밀번호가 회전되지 않는다」는 공식 문서가
아니라 **프로젝트 이슈 트래커**에서만 확인됐고, 감시 범위와 RBAC의 관계는 1차 대조를 **못 했다**.
그 둘은 **이 프로젝트에서 관측한 것**이지 문서화된 계약이 아니다.

## 그래서 무엇을 배웠나

**오퍼레이터는 기능이 아니라 층이다 — 그래서 「쓴다/안 쓴다」가 아니라 「어디에 두는가」다.** 같은 클러스터에
층이 있는 것과 없는 것이 공존하고, 판정을 가른 것은 제품 품질이 아니라 **유실 급소·상주 순증·전제 일치**다.

**선언이 짧아진 만큼 내가 안 쓴 것이 늘어난다.** CR에 없는 필드가 파드에 있다 — 갭으로 읽으면 없는 문제를
고치고, 덮어쓰려 하면 충돌을 만든다. **정적 감사는 선언만 보므로 이 층에서 거짓말을 한다.**

**`status`의 소유자가 내가 아니라는 것이 대가의 본체다.** 조정 루프가 도는 것과 그 결과가 내게
도달하는 것은 다른 축이고, 후자가 끊겨도 **양쪽 다 초록**이다. 어느 쪽도 거짓말을 하지 않는데 틀린다.

**위임한 것은 되찾을 때도 남의 손을 거친다.** finalizer는 붙인 쪽만 뗄 수 있어 컨트롤러가 먼저 사라지면
삭제가 멈추고, 초기화 1회 필드는 다시 선언해도 반영되지 않는다. **「선언형」은 리소스가 아니라 필드의 성질이다.**
